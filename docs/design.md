## Process model

- One static Go binary, `linux/arm64` (Pis) and `linux/amd64` (grok-bot-box). It is deterministic and runs no LLM.
- It opens no listen socket of any kind. Its only network peers are bot-api-server (outbound `wss://`) and, for probes, `127.0.0.1:<exposed port>`.
- It refuses to start if: euid is 0; `BOT_AGENT_SERVER_URL` is not `wss://`; the env file mode is not 0600; or, in phase 2, `DOCKER_HOST` is empty, `tcp://`, or the raw engine socket.
- `bot-agent version` prints the version. There is no `env` subcommand and nothing else prints configuration.

## Configuration

`/etc/bot-agent/env` (mode 0600, owner `bot-agent`, directory 1770 sticky `root:bot-agent`):

```
BOT_AGENT_SERVER_URL=wss://<api-host>/agent/v1/ws
BOT_AGENT_JOIN_TOKEN=<one-time; removed after enroll>
BOT_AGENT_HOST_ID=<written on enroll>
BOT_AGENT_CREDENTIAL_ID=<written on enroll>
BOT_AGENT_CREDENTIAL=<written on enroll; rotated by the server>
```

Rewrites are atomic: temp file in the same directory, mode 0600, fsync, rename. The directory is sticky so the agent can rename that temp file over `env` and cannot unlink the root-owned `runner.toml`. Collection intervals and health checks come from the server in `hello_ok.config`. The agent clamps them (host metrics 5–60 s, processes and health 30–300 s, at most 50 checks).

## Phase 1: read-only

| Area | What | Matches Telegraf today |
|---|---|---|
| Host compute | cpu (`cpu-total`, `usage_idle`, …), mem, disk (`/`), diskio (whole disks), net (no `lo`), system (load1/5/15, uptime), temp (`cpu_thermal` where present) | Same names and units as `docs/api-contract.md`, so the overlap comparison is like for like. |
| Processes | Top 20 by cpu and top 20 by RSS each interval, plus every process of a known service. Irix cpu (100 = one core). The agent truncates `cmdline` to 1024 characters and redacts secrets (agent-protocol §Redaction, `internal/agent/redact`) before sending; the server redacts again on ingest and shortens it for display. | procstat scan + topk |
| Services | Discovery: listening TCP sockets → pid → systemd unit (via `/proc/<pid>/cgroup`) or process. Reported in `hello`, when they change, and at least every 5 minutes while connected; see agent-protocol v1.2. | `services/*.json` (hand-written) |
| Health | `probe_health` per configured check: `http://127.0.0.1:<port><path>` or a TCP connect. The port must be one the service is listening on (D12). No redirects; timeout ≤ 10 s; body not stored, only status, latency, and result. | `inputs.http_response` |
| Live tasks | `host_snapshot`, `probe_health` | — |

A services report is the host's full set, so the agent sends one only from a complete discovery: the process scan succeeded and, when the program policy is enabled, the helper's owned-program lookup succeeded and, when images are enabled, `container_list` succeeded. If any of those fail, that cycle sends no `services` frame and the previous report stays. `hello` includes `services_complete`, which is false with `services` empty when the first discovery did not finish, so the server does not store that hello as the full set (agent-protocol v1.3.2).

The user-scope systemd caveat from spec-v1 still applies: a system user cannot read another user's bus. Units are inferred from the cgroup path, which needs no bus.

## Phase 2: logs, deploy, run/stop

The Docker socket proxy below is superseded by agent-protocol v1.4: `bot-agent-runner` opens `/var/run/docker.sock` itself. See Images.

- **Docker socket proxy:** a separate unit, the only process that opens the engine socket (raw socket access is root-equivalent). It listens on `/run/bot-agent/docker.sock` (mode 0600, owner `bot-agent`). Allowed calls:
  - `GET /containers/json`, `GET /containers/{id}/json`, `GET /containers/{id}/logs`;
  - `POST /containers/{id}/start`, `POST /containers/{id}/stop`;
  - `GET /images/{name}/json`, `POST /images/create` (pull, no registry auth);
  - `POST /containers/create`, only after the body is validated. It rejects `Privileged`, `CapAdd`, `Devices`, `Binds`, bind-type `Mounts`, `NetworkMode=host`, `PidMode=host`, `IpcMode=host`, `UsernsMode=host`, and `User` 0/root. It requires the label `dev.deploybot.owner=bot-agent`.

  - *For redeploy (umbrella §5.3, D30):* `POST /containers/{id}/rename` and `DELETE /containers/{id}` (never `v=1`), only for containers labelled `dev.deploybot.owner=bot-agent`.

  Everything else is denied: build, exec, attach, kill, commit, volumes and networks endpoints, and swarm. Body validation is why a small custom proxy is recommended (umbrella D26).
- **Owned list:** `/var/lib/bot-agent/owned` (mode 0600), one container name per line. Only a successful `deploy` adds a name and only undeploy removes one. `logs`, `run`, and `stop` refuse names that are not on it (`not_owned`), whatever the server says.
- `deploy`: if a container with `container_name` exists, adopt it (owned list only; the container is untouched). Otherwise pull the image if needed, create the container from the closed spec (umbrella §5.2), start it, and add it to the list.
- `redeploy` (umbrella §5.3, D30): created containers only. Pull first, stop and rename to `<name>-prev`, create and start the new container, wait for health, and on failure roll back to `-prev`.
- Secrets (umbrella §5.4, D31): values arrive only inside a deploy/redeploy task frame as `secret_env`. They go straight into the Docker create body. They are never written to `tasks/`, the spool, or the journal, and are redacted by exact value from logs and results. `status` results never include `Config.Env`.
- `logs`: tail 1–1000 lines, stdout/stderr flags, no follow. Redacted with the shared regex and capped at 64 KiB. Viewers may request it (umbrella D19).
- One mutating task per service at a time. Task files are kept under `/var/lib/bot-agent/tasks/<task_id>.json` so a result survives a reconnect. A mutating task that was not finished when the process restarted is reported `failed`/`agent_restarted` and is not re-run.

## Every task, before running

1. `host_id` matches the enrolled host.
2. `expires_at` has not passed (clock corrected by the `hello_ok.server_time` offset).
3. `kind` is in this phase's allowlist and in the build's capabilities.
4. The service is known; for logs/run/stop it is also owned.
5. `spec` keys are from that kind's closed set.

Image tasks add four checks after the host, expiry, kind, and closed-key checks, in this order: the policy is valid and images are enabled (`policy_denied`); `project` is in `projects` (`policy_denied`); ImageSpec and entry field rules (`bad_spec`); the image matches an `images` pattern (`policy_denied`). A non-null `service` is `bad_spec` before the policy check. The frame's `timeout_sec` is the deadline for the whole image sequence, clamped to at most 4020 seconds. Zero or negative uses 15 seconds. Program tasks keep the 15–60 second cap.

## systemd unit (sketch; Joe installs)

The v1 hardening carries over ([v1 §10](../../docs/design-bot-agent-deploy.v1.md)): `User=bot-agent`, no supplementary groups, `NoNewPrivileges`, `ProtectSystem=strict`, `ReadWritePaths=/var/lib/bot-agent /etc/bot-agent`, empty `CapabilityBoundingSet=`, `InaccessiblePaths=-/run/docker.sock -/var/run/docker.sock -/var/lib/bot-agent-runner` (the leading `-` lets a host without that path start), and `EnvironmentFile=/etc/bot-agent/env` (no leading `-`). Unit `bot-agent.service`, binary `/usr/local/bin/bot-agent` (accepted). The legacy `bot_agent.service` and `/usr/local/bin/bot_agent` are removed by Joe on pi2, pi3, and pi4 after the new agent is up (umbrella D24). The agent's installer never touches them.

## Programs (v1.3)

Wave 1 of `docs/spec-project-catalog.md`, amended by agent-protocol v1.3.1 and v1.5.1, is a root helper, not a capability on `bot-agent.service`. `cmd/bot-agent-runner` is installed at `/usr/local/libexec/bot-agent-runner` (`root:root`, `0755`). systemd accepts `/run/bot-agent-runner.sock` and starts one `serve-conn` process per connection. The agent dials that socket. The connect budget is 5 seconds. The rest of the call uses the task timeout (`timeout_sec`, clamped to 15–60 seconds); hello and discovery keep a 5 second limit. It does not resolve paths under `/home`. The helper re-validates the root-owned policy and the task, including realpath and exec resolution, writes `/etc/systemd/system/deploybot-<project>-<entry>.service` (`root`, `0644`, with `[Install]` / `WantedBy=multi-user.target`), `/var/lib/bot-agent-runner/programs/<unit>.env` (`root`, `0600`), and the same request at `/var/lib/bot-agent-runner/programs/<unit>.json` (`root`, `0600`). The `programs` directory is `0700`. The unit's `EnvironmentFile=` is that env path. `start` writes the env file, then the spec, then the unit, then runs `daemon-reload`, `enable`, and `restart`, so a program that was running is started again at boot. A `\` in the directory, the executable, or the `run_as` home is `policy_denied` before any write. A drop-in at `/etc/systemd/system/<unit>.d` or `/run/systemd/system/<unit>.d` (any type) is `io_error` before `enable` on `start` and `restart`. The helper never creates or removes a drop-in. A `restart` of a unit already in `/etc` does not rewrite it, and still runs `daemon-reload`, `enable`, and `restart`. `stop` runs `disable`, `stop`, then removes every regular file it owns among the unit, env, and spec, including an owned `/run` copy. It keeps going when one cannot be removed, never unlinks a symlink, runs `daemon-reload`, and replies `io_error` if a file it tried to remove remains. A later stop with no unit file removes a leftover spec whose stored project and entry match. Otherwise a stopped program leaves nothing behind. `packaging/tmpfiles.d/bot-agent-runner.conf` still creates `/run/bot-agent` and `/run/bot-agent/env` at boot (`0700` `root:root`); the helper creates them too, because the lock, the image locks, and a not-yet-migrated env file live there. A start whose `daemon-reload` or `enable` fails, or whose unit does not become freshly active, disables and stops that unit, removes the `/etc` files and an owned `/run` copy, runs `daemon-reload` after those files are gone, and is `start_failed`. If that cleanup cannot remove a file, or `disable` fails, the reply is `io_error`. If `daemon-reload` fails while `restart` is moving a unit off `/run`, the helper removes the `/etc` files it just wrote and keeps the `/run` files, with no second reload. If `enable` fails after that reload, it removes those files and runs `daemon-reload` again so the `/run` unit is loaded. Both are `start_failed` with `fresh` false. A failure after `enable`, or a failure of a unit already in `/etc`, keeps the `/etc` unit enabled. `max_programs` counts unit files, not only active units. A name in both `/etc/systemd/system` and `/run/systemd/system` counts once. `status`, `logs`, `sockets`, and `list` look in `/etc` first, then `/run`. Restart re-checks the stored request against the current policy and stops a unit that is no longer allowed, except a restart refused because its project is not listed (below), which keeps the unit. The next `start` of a unit this helper still owns under `/run` writes the `/etc` copy and removes the `/run` unit and `/run/bot-agent/env/<unit>.{env,json}` in that same verb. `restart` writes that `/etc` copy only when it is missing and removes the `/run` files only after `enable` succeeds. `stop` removes an owned `/run` copy together with the `/etc` files. The helper refuses a foreign file in `/etc` with `not_created` whatever is in `/run`, and that owned `/run` unit still counts for `max_programs`. `list` does not return it. Our unit in `/etc` wins over a foreign same-name file in `/run`: the verb acts on `/etc` and leaves the `/run` file untouched. `bot-agent-runner@.service` `ReadWritePaths=` includes `/etc/systemd/system` so the helper can install those units; `bot-agent.service` is unchanged and already hides `/var/lib/bot-agent-runner`. Tests drive systemd, journalctl, and the socket through fakes. See `NOTES.md` for what still has to be confirmed on pi1.

**Program secrets (agent-protocol v1.11).** `program_start` takes an optional `secret_keys` list. `programs.Check` is shared by the agent and the helper: every listed key must be in `env`, a secret-looking key is allowed only when listed, and listed keys meet every other env rule and the denylist. The helper stores `secret_keys` in `<unit>.json` (left out when the start had none, so older specs are byte-for-byte the same) and the restart re-check accepts it. The env file is unchanged. When a start replaces a stored spec, the helper carries the old spec's secret values (6 bytes or more, not current again) into a helper-only `retired_secrets` list in the new spec, newest 64 kept; `recheckSpec` drops that key before `programs.Check`. The helper's `logs` verb takes the helper lock, reads the stored spec's current and retired values before running `journalctl`, cuts the journal at the last line end within 1 MiB, and applies exact-value redaction (`redact.NewExactEnv`, the preview form) before the keyword regex. A missing, unreadable or malformed stored spec makes `logs` `io_error`, not unredacted output. The agent zeroes a program task's spec bytes when the task ends. The agent applies the start frame's own listed values to a `start_failed` tail. The agent holds no values after the task, so `program_logs` and `program_status` rely on the helper's pass. `hello.programs.secrets` is true.

**Projects gate (agent-protocol v1.12).** `program_start` and `program_restart` need a project that matches the slug grammar and is in `projects` with no overlapping pair (`Policy.ProjectAllowed`), in both the agent (`task_reject` `policy_denied`) and the helper; a bad slug is `policy_denied` on those two kinds and stays `bad_spec` on the others. The gate sits in `programs.Check`. The helper loads the policy once per request, after taking its lock, and the restart re-check uses that snapshot; a stored spec whose project the snapshot does not allow is refused without the removal path, so the unit keeps running. `stop`, `status`, `logs`, `sockets` and `list` are not gated. At start, with an enabled policy, the agent asks the helper for `list` once (capped at 5 seconds) and logs `bot-agent: program unit <unit> is for project <slug>, which is not in projects` for each owned unit of an unlisted project; it stops nothing. `hello.programs.projects` is the valid policy's list (`[]` otherwise), sent whenever `hello.programs` is; a policy with more than 32 projects is `parse`.

Threat model, from the catalog spec: a compromised API cannot change `/etc/bot-agent/runner.toml`; a compromised agent stays unprivileged and cannot exceed that file, because the helper checks every request again and the peer uid must be `bot-agent`. Polkit can constrain unit names and still let a transient unit run as root, which is why the helper is the privileged step. There is no shell unless `allow_shell` is true. Env values are not logged. `bot-agent.service` gains no capability. `ProtectHome=read-only` on a program unit leaves other homes readable, and an allowlisted interpreter runs the caller's arguments as `run_as`. Both follow from the host owner choosing `run_as` and `exec_allow`. The v1.20 agent upgrade keeps this model: the server names only a version, and the host decides what runs, from where, checked against a key the server does not hold (see "Agent upgrade from the server").

Rollback is local. Set `enabled = false` and restart the agent, or `systemctl disable --now bot-agent-runner.socket`. New tasks stop. Units already enabled keep running, and an enabled unit comes back at the next boot, until an administrator runs `systemctl disable --now 'deploybot-*'` and removes the unit, env, and spec files. Disabling only the helper does not disable those units. The agent reads the policy only at startup, so `enabled = false` does not take effect until that restart. After that it no longer reports those units as owned services, and it will not stop them itself.

## Images (agent-protocol v1.4)

`internal/agent/images` is the shared vocabulary. `internal/runner` owns the Engine client and the verbs. The agent does not import `internal/runner`. It calls the ten image verbs through the existing helper client in `internal/agent/run`.

Agent task kinds are `image_deploy`, `image_rollback`, `image_remove`, `image_start`, `image_stop`, `image_restart`, `image_status`, and `image_logs`. Specs use the v1.4 closed key sets. `hello.programs.images` follows `ImagesEnabled` (valid, enabled, both lists non-empty, and no listed project is another plus `-` plus more characters). `hello.programs.docker` follows the latest discovery pass's `container_list` (agent-protocol v1.17): success is true, failure false. The agent remembers what the session's `hello` sent; when two passes in a row disagree with it, the session loop returns `conn.ErrReconnect` and the next `hello` carries the new value. A one-pass blip does nothing. The loop does not reconnect while a task is running or waiting (`tasksBusy`); the change stays confirmed and is tried at the next pass. A change to false reconnects at most once per `dockerReconnectGap` (5 min), so a flapping daemon cannot loop sessions; a change back to true reconnects as soon as it is confirmed. The `container discovery failed` line is logged once per run of failed passes (a successful list re-arms it). `hello.programs.files` is true whenever `programs` is sent. `hello.programs.docker_health`, `hello.programs.healthcheck`, `hello.programs.logging`, `hello.programs.health_policy`, and `hello.programs.env_hash` are true the same way. The agent calls `container_list` only when images are enabled, including when the scan or the program lookup already failed, and it merges containers only when that cycle is still complete.

Service deploy is `image_pull`, then `container_status`. Running this digest with this `spec_hash`, this `files_hash`, and `force` false is `unchanged`. When the spec has a `healthcheck`, `unchanged` also requires that container's `container_list` health to be `healthy`. The agent computes `files_hash` from the task's files; it is empty when there are none. When the task has `env_hash` (v1.14), `unchanged` also requires the container's `dev.deploybot.env_hash` label to equal it; a container without the label is changed. Otherwise `container_deploy`, then a health wait: the entry's configured `http` or `tcp` checks on `127.0.0.1` when the port is one of the spec's host ports, or else `running` with `restart_count` 0 for `healthy_after_sec`, polled every 2 seconds. A service whose spec has `healthcheck` polls `container_list` every 2 seconds instead, until `health` is `healthy` and those checks pass; each poll also reads `container_status`, because the list has no restart count. `starting` keeps waiting. v1.16 (spec `docs/spec-deploy-stuck.md`): in all three waits `restart_count > 0` or state `restarting` is not healthy (`restartLoop`), so a crash loop fails at its first restart, and a `container_status` state of `exited`, `dead` or `missing` (`terminalState`) ends every wait, the `container_list` wait included, so a service with restart `no` that crashes fails at once. `restart_count` is Docker's count for the container's current run; a kept container swapped back by `image_rollback` is started through the API, which resets it (to be confirmed in the pi3 live check). `runImage` gives the wait its own context and deadline (`healthWindow`), a child of the task context that ends `failReserve` (60 s) before the task deadline when the budget is over 60 s (`waitBudget`); the failure path (rollback, stop, tail, status) keeps the task context. This applies to service deploys and to every `image_rollback`, including the kept-container swap; a job deploy's own wait is unchanged. The budget (`imageBudget`) is the frame timeout, or with `healthcheck` `max(timeout_sec, start_period_sec + interval_sec × (retries + 1))` where `timeout_sec` is the task frame timeout. The healthcheck floor loses the reserve too: the budget is deliberately not raised by 60 s, so the agent never outlasts the API's wait for the task. Both deadlines count from the task start, so a pull that runs past budget − 60 s ends the wait at once. `unhealthy`, or the wait limit (that budget less the 60 s reserve), calls `container_rollback` only when the container before this deploy was `running`, and otherwise stops the new container and reports `failed`. `image_rollback` uses the same wait. Without `healthcheck` the wait is unchanged. A failed wait calls `container_rollback` and finishes `rolled_back` or `rollback_failed` only when the container before this deploy was `running`. Any other state stops the new container and reports `failed`, and a parked container stays on `-prev`. A `container_status` error during that wait, including `docker_unavailable`, is `failed` and does not roll back. A job pulls, removes a container that is present, deploys, and polls every 2 seconds until `exited` or the spec `timeout_sec` (10..3600). Exit 0 is `succeeded`; any other exit is `failed` with `exit_code`; the deadline stops the container and the outcome is `timeout`. Cancelling the task context is `failed` and does not stop the container. An image task spec may be as large as the 1 MiB agent frame. Image helper verbs accept up to 2 MiB. Program verbs stay at 64 KiB. A helper body over its verb's limit is outcome `failed`. A service `image_rollback` whose digest equals the kept container (`container_status.prev.digest`) swaps that container back with `container_rollback` and does not pull. Healthy is `succeeded` with that digest; not healthy is `failed`. When the task has `env_hash`, the swap also needs `container_status.prev.env_hash` to equal it; otherwise the rollback pulls by digest and creates a new container with the task's env and spec. When the spec has `healthcheck`, that wait is the `container_list` wait. Other digests still pull `<name>@<digest>` and deploy. Job rollbacks stay on the pull path. The other kinds are one verb each. `task_result.status` is `succeeded` only for `succeeded` and `unchanged`; otherwise it is `failed` and `error_code` is the outcome. Helper refusals `{"error":...}` and transport refusals `{"ok":false,"reason":...}` both map: `image_unavailable` and `conflict` stay, `policy_denied` and `bad_spec` become `forbidden_spec`, and `docker_unavailable` or a transport error becomes `failed`.

Env hash (agent-protocol v1.14, umbrella spec `docs/spec-env-generate.md` §3.7). `tasks.ImageReq.EnvHash` is the optional task `env_hash`: present means `images.ValidSpecHash` (64 lowercase hex), else `bad_spec`; `null` is absent. `images.DeployRequest.EnvHash` (omitempty) carries it to the helper, which re-checks it and sets `images.LabelEnvHash` in `containerLabels` only when non-empty. `container_status` returns the label as `env_hash` and `prev.env_hash`, omitted when absent or malformed. The agent compares it only when the task has one, so a task without it is v1.9. The supervisor's automatic rollback has no task `env_hash` and swaps `-prev` regardless of its label. A new agent with an old helper would see the helper refuse `env_hash` as an unknown field; both ship in one package.

Health failure policy (agent-protocol v1.9, spec `docs/spec-health-policy.md`). `images.ImageSpec.HealthPolicy` holds the optional keys as pointers, so an explicit `0` or `""` is refused instead of defaulted; `Health()` fills `rollback`, `none`, 45, 3. `Validate` refuses unknown keys (strict decode), bad enums, out-of-range numbers, the key on a job, an `on_unhealthy` action without the entry's `healthcheck`, and `keep` with an `on_unhealthy` action (rev 2), in the agent and again in the helper. `deployService` reads `on_deploy_failure` only for `image_deploy`: `rollback` is the v1.6.1 path unchanged, `stop` calls `container_stop` whatever the pre-deploy state, and `keep` leaves the new container running; both report `failed` with the current status and tail. The helper adds the three `dev.deploybot.on_unhealthy`/`unhealthy_after_sec`/`max_actions_per_hour` labels at create when `on_unhealthy` is not `none`, and `container_list` returns them as `policy` for rows with the owner label (`images.PolicyFromLabels`; an invalid value is null). `keepLabels` is unchanged, so the policy labels are not in `labels`. The supervisor (`internal/agent/run/supervise.go`) runs from `Run` when images are enabled, every `Options.SuperviseEvery` (15 s). Each poll lists containers; a failed list ends every unhealthy streak. It considers owned current containers (name `<project>-<entry>`, host label, project allowed) with a non-`none` policy, and only `running` + `unhealthy` ones extend a streak. The per-entry lock (`entryLock`) is a shared/exclusive lock with a cancellable shared side: every image task takes the shared side for its whole run, waiting for a running supervisor action only within its task context (on timeout it is `failed` and calls no helper verb), so tasks are not serialised against each other; the supervisor only tries the exclusive side, so it never waits and never acts during a task. The supervisor does nothing when `machineHost()` is empty (unreadable machine-id), and the host label must match. Under that lock it checks the threshold, the sliding one-hour action window, and for `rollback` the once-per-deploy flag and a listed `-prev` (the `<project>-<entry>-prev` name with the same owner, project, entry and host labels; a name squatter counts as no `-prev`); a block marks the entry `gave_up` once. `image_deploy` and `image_rollback` clear the entry's state when they finish, before releasing the lock. Actions are `container_restart` or `container_rollback` with a 60 s context, longer than the helper's 30 s stop grace (`images.StopGraceSec`), then a `container_status` read with its own 5 s context (65 s budget, rev 3); a failed call still counts, reports `result` `error` with a null digest, and skips the status read. Otherwise the digest is the running container's after the action; when that read fails or has no digest, it is the digest the poll already knew (the current container for restart, the listed `-prev` for rollback), or null when none was listed. `gave_up` sends the listed current digest. Frames go to an in-memory queue (cap 100, oldest dropped) that the session sends after `replay` on each connection and whenever the queue wakes the loop; `auto_action_ack` removes a frame. Nothing is persisted: counters and unsent frames are lost on agent restart.

Discovery names an owned container (four labels, host label, project in `projects`) exactly by its entry, with `owner.kind` `image`. A non-owned row that collides is renamed. An owned row that already has the name keeps it, and the extra container is omitted rather than suffixed. The host label is `images.HostID` of `/etc/machine-id` when that file is readable under the agent sandbox. If it is not, any non-empty host label is accepted and the agent logs that once, without the path. The `-prev` slot is not a second discovered service; its host ports are still dropped from the unmapped list, and a lone `-prev` container is the owned service. Every other container is `kind` `container`, named by the container name without one leading `/`, with `image_digest` null and `"owner":null`. `image_digest` is present on every discovered row. Published host ports are not also reported as unmapped listeners. `container_list` returns at most 200 containers, Deploybot-labelled rows first, with `truncated` set when it cut. A truncated list is still a complete discovery, and the agent logs that once. Each item's `health` is `healthy`, `unhealthy`, `starting`, or null. While `config.docker_health` is true, a complete pass emits one Docker `health` sample for each container service that is `healthy` or `unhealthy`. `starting` and null emit nothing.

Env values, `registry_auth.token`, and file contents live only for the task. They are not logged. The spec bytes are zeroed when the task returns, and the pending result has no env object and no file content. Exact-value redaction (`internal/agent/redact`) replaces the registry token and the secret-file values from v1.5 with `[REDACTED]` (the whole content when it is 6–4096 bytes, trimmed lines of 16–4096 bytes, and JSON string values and their lines in that same line range). When `secret_keys` is absent, every env value of at least 6 bytes is included too. When `secret_keys` is present, only those env values are included, and a key that is not in `env` is `bad_spec`. Deploybot replaces an env secret with its preview: the first four runes and `…` when the value has at least 16 runes, otherwise `••••`. Forms are the raw bytes, base64 standard and URL (padded and raw), and both JSON-escaped forms, before the v1.0.1 regex, and this applies only to that task's result strings and log lines. `outcome`, `digest`, `exit_code`, and status fields are passed through as the helper returned them. Deploy and rollback tails send the token and file pieces on `container_logs` `redact` and the env values on `redact_env`. Each list is clipped to 2048 values, 6–4096 bytes each, and 512 KiB. The helper applies them to each raw line before the regex and the 2048-character cut, and does not log or return either list. `image_logs` sends neither list. This is best-effort. It is not a secrecy boundary (spec §3.4 and §12.9): the agent sees the values, and a container can print them in another encoding or send them over the network.

The helper talks to Docker Engine on `/var/run/docker.sock` with a small client of fixed methods. Each `engineClient` (one per helper run) negotiates before its first request: `GET /_ping` (unversioned), read `API-Version`, speak `/v<min(1.47, daemon)>` (agent-protocol v1.17). A missing or unreadable header is taken as 1.41 and logged; below 1.41 (Docker 20.10, the first with `HostConfig.CgroupnsMode`) or a failed ping, every request is `errEngine` (`docker_unavailable`) and the helper logs why. Below 1.44 network create sends `CheckDuplicate: true` (Docker 25 refuses duplicate names by itself), and `container_deploy` with shared `networks` returns the helper-to-agent reason `shared_networks_need_docker25` after `buildCreate` and before any other Engine call; the agent reports outcome `failed` and puts a fixed line about Docker 25 in front of the last 49 log lines (50 in all). For a job with shared networks the agent skips its own `container_remove` before `container_deploy`; the helper's `deployJob` removes the previous container after its checks, so a refusal keeps it. `container_rollback` (the swap to the kept container) creates nothing and is not refused. The ping runs under its own `pingTimeout` (5 s, or the caller's deadline if sooner). Engine answers of 400 and up (except a 404 on a GET or DELETE and a 409 on a volume or network create) and requests with no answer are logged as `bot-agent-runner: docker: <method> <path>: status <n> (API <v>): <quoted message>`; the message is the Engine `message` cut to 300 bytes after the request's registry token or create env values and the journal secret patterns are redacted, and it is replaced with `message withheld` when one of those values is shorter than 6 bytes (exact redaction could miss a short value). Bodies, headers and queries are never logged. `docker_check` is the installer's verb: not policy-gated, one ping, it answers `present`, `api` (the daemon's; empty when the header was missing), `ok`, `networks_ok` and `reason` (`ok`, `ok, API assumed 1.41`, `absent`, `not answering`, `too old`); the agent's socket client refuses to send it. A deploy whose spec has `healthcheck` sends Engine `Healthcheck`: `Test` is `CMD` plus the argv, and `Interval`, `Timeout`, and `StartPeriod` are nanoseconds. The key is absent when the spec has no `healthcheck`, so the image default stands. List rows read `Health.Status` when that object is present (API v1.52); otherwise they read the `Status` suffix `(healthy)`, `(unhealthy)`, or `(health: starting)`. URL path segments are escaped. Containers are addressed by the id from the helper's own name lookup. Query strings are built from typed values. Response bodies are size-capped. Tests use a fake Engine on a unix socket. There is no Docker SDK and no real Docker in the unit tests. Stop uses `t=images.StopGraceSec` (30). `container_restart` and `container_rollback` of a running container run every step from the stop on under `finishCtx`, which is `context.WithoutCancel` of the verb context bounded by `finishBudget` (60 s), so a caller that gives up (the socket-close watcher cancels the verb context) cannot leave the container stopped (agent-protocol v1.9 rev 3). Restart starts the container after the stop, even if the stop failed (starting a running container is a no-op). Every deploy (service or job), rollback and remove reads its pair through `loadPairClearing`. From the same list, it first removes a leftover `<name>-old` that passes `images.OwnsLabels` for the entry, together with its `.new` slot, and leaves it out of the `max_containers` count. A container on that name with other labels makes the verb return `conflict` and is not touched (rev 3b). A rollback of a running container (`rollbackRunning`) then, on `finishCtx`, it stops the original, renames it to `<name>-old`, moves its slot to `<name>.new` and `-prev`'s slot to the current name, renames `-prev` to the current name, and starts it. Only then does it remove the original and the `.new` slot. On any failure `restoreOriginal` runs on a fresh 20 s `recoverCtx` that is not derived from `finishCtx`; the restart's start after its stop uses one too. It lists containers (a failed rename may have landed; without a list it renames blind), puts `-prev` and the original back on their names, undoes exactly the slot moves that happened, and starts the original by id. Slot-restore failures, and a failed final remove of `-old` after `-prev` started, are logged; the latter rollback still succeeds. The verb still returns the refusal. A rollback of a non-running container keeps the previous remove-then-swap path. Deploybot sets `HostConfig.LogConfig` on every container create to the json-file driver with `max-size` and `max-file` (10m and 3 unless ImageSpec `logging` is set), and `hello.programs.logging` is true.

`bot-agent-runner@.service` sets `RuntimeMaxSec=900` and adds `/var/run/docker.sock` to `ReadWritePaths`. It also sets `StateDirectory=bot-agent-runner` and `StateDirectoryMode=0700`, so `/var/lib/bot-agent-runner` exists and is writable under `ProtectSystem=strict`. The helper creates `files/` under that directory. The other hardening stays: `ProtectSystem=strict`, `PrivateDevices=yes`, `RestrictAddressFamilies=AF_UNIX`. The socket is `AF_UNIX` and is not under `/dev`. `bot-agent.service` sets `InaccessiblePaths=-/run/docker.sock -/var/run/docker.sock -/var/lib/bot-agent-runner`. The leading `-` on the store path lets a host without that directory start. Joe reviews these unit lines before install.

Threat model, from spec §3: one root process opens the socket; nothing from a request reaches Docker as raw HTTP; projects and labels scope mutations; env values, registry tokens, and file contents are not returned; the policy ceiling is the image patterns, the project list, project volumes, managed files, the project bridge, and public ports only when `allow_public_ports` is set. The bind source of a managed file is built by the helper. A symlink or a failed ownership, mode, or link-count check is `bad_spec` and does not touch a container. Mounts are read-only and carry no `BindOptions`. The agent cannot open the store.

Managed files (v1.5) live at `/var/lib/bot-agent-runner/files/<project>-<entry>/<name>`, with `-prev` and `.new` slots beside the current one. The helper walks that directory from `/` with `openat` and `O_NOFOLLOW`, then creates slots and files only through `*at` calls. A service deploy writes `.new`, parks the current container and its slot as `-prev`, and renames `.new` into place before create. A job replaces its one slot. Rollback removes the current container and its slot, renames `-prev` and its slot back, and starts. If a container rename returns an error, the helper lists the entry again on a short context of its own, because the request context may already be cancelled, and moves the slot onto the name that container actually has. A container still named `-prev` gets that slot back. A rename that landed keeps the slot on the current name. The same list runs when parking the current container as `-prev` and when a failed start renames it back. If that list cannot show exactly one of the two names with this entry's labels, the slot stays put and the verb returns `docker_unavailable`. A start that fails after the container is back on `-prev` still moves the slot with it, so the names match. `container_remove` deletes the container and its slot. A missing `files/` directory, or a missing parent, on a verb with no files is "no store" and the container change still happens. A request with files creates `files/` when the parent exists. A missing parent on that request, and any other failure to open the store, changes nothing. When `files` is non-empty the container label `dev.deploybot.files_hash` is the hex SHA-256 of `<name>:<hex sha256 of content>\n` sorted by name. `container_status.files_hash` is that label, or `""` when there is none. The store path is not configurable from the request or from `runner.toml`.

`runner.toml` keys, all invalid when the value is the wrong shape: `images` (patterns), `projects` (slugs), `max_containers` (1..200, default 20), `allow_public_ports` (default false). `ImagesEnabled` is true only when the policy is valid and enabled, both lists are non-empty, and no listed project is another plus `-` plus more characters. When two projects overlap that way, the helper logs `bot-agent-runner: policy: overlapping projects <a> <b>` once on that connection. The example file leaves these keys commented out and says that container access equals root.

Shared networks (agent-protocol v1.13, agent 0.2.9) amend the one-network rule. Root defines them in `runner.toml`: `shared_networks` items `<name>=<cidr>` (name `^[a-z0-9][a-z0-9-]{0,31}$`, at most 8, unique; an IPv4 CIDR in canonical form inside RFC 1918 with a prefix of 16 to 28, no two overlapping) and `shared_network_projects` items `<name>:<slug>` (the network defined, the slug in `projects`, no duplicates, at most 32). Any violation makes the policy invalid (`parse`). `hello.programs.shared_networks` sends `[{name, subnet, projects}]` in file order from a valid policy, `[]` otherwise. An ImageSpec may carry `networks`, 1 to 4 unique names; an empty array, a duplicate or a bad name is `bad_spec`. The agent pre-check and the helper re-check (in `precheckDeploy`, before the flock and any Engine call) refuse a name that is not defined or does not list the task's project with `policy_denied`. For each name the helper ensures `deploybot-shared-<name>` before the current container is stopped, parked or replaced (an owned leftover `-old` may already have been cleared); the project network is also ensured before any stop, so a project network name held by another network is `conflict` with the current container still running: inspect (driver, labels, `IPAM.Config[].Subnet`); when missing, create it as `bridge` with the labels `dev.deploybot.owner=bot-agent`, `host`, `kind=shared` and `network=<name>` and `IPAM.Config=[{Subnet}]`, then inspect again. A 409 on create is a lost race and is inspected too. An existing network must have that driver, those four labels and exactly one subnet equal to the policy's, otherwise the verb is `conflict` and the helper logs `bot-agent-runner: shared network deploybot-shared-<name> exists with a different subnet or labels; remove it by hand (docker network rm) after stopping its containers`. A create Docker refuses because the pool overlaps is `conflict` with the log line `bot-agent-runner: subnet <cidr> overlaps an existing Docker network`. The refusal body stays `{"error":"conflict"}`; the helper wire has no text field, so the diagnostic is in the helper's journal only. The agent and the helper never remove or recreate a shared network; `install.sh remove --remove-workloads`, the operator teardown, is the one exception. The create body adds one `EndpointsConfig` entry per shared network with no `Aliases` and no address; `NetworkMode` stays the project network, and a spec without `networks` gives the same bytes as 0.2.8. A project whose slug is `shared-<name>` cannot join shared network `<name>`: its project network has the same name, so the helper answers `conflict` before any Docker call. Other members reach the container by its name `<project>-<entry>`. The `-prev` container keeps the networks it was created with, so after a member or network is revoked a rollback or a start of a container created on the network re-attaches it; removing the container ends the attachment.

Verbs: `image_pull`, `container_deploy`, `container_rollback`, `container_remove`, `container_start`, `container_stop`, `container_restart`, `container_status`, `container_logs`, `container_list`. Mutating entry verbs hold `flock` on `/run/bot-agent/image-<project>-<entry>.lock` for the whole verb. `container_status` and `container_logs` do not take that lock and do not create the file. At most 512 of those files are created. A further new name is `policy_denied` and does not dial. The file is not removed on unlock. `container_deploy` also holds `/run/bot-agent/image-count.lock` across the container count and the create, so the host cap covers every entry. Program verbs keep the helper-wide lock. Pull and list do not take the entry lock. Rollback reads the previous container's image from the helper's own list and refuses it unless that image is `repo@sha256:<64 hex>` and the repo is still in `images`.

Rollback for containers: `images = []`, or an empty `projects` list, makes the helper refuse image verbs. Containers already created keep running. Removing `/var/run/docker.sock` from `ReadWritePaths` is the other switch.

## Installer and `policy check`

`packaging/install.sh` is the host install path from v0.2.1. It ships in the release bundle and copies only files from that directory (no download). Subcommands are `check`, `install`, `enroll`, `upgrade`, `rollback`, and `remove`. State is `/var/lib/bot-agent-installer/` mode `0700` root: the installed version and the sha256 of every file the installer wrote, plus `prev/` for the last upgrade. Upgrade copies a replaced file to `<file>.prev` (one level). A failure after that backup is written restores it and exits 1. A successful upgrade keeps `.prev` until a later restore has been verified. When `/etc/bot-agent/env` exists, upgrade and rollback restart the agent whatever its previous state; `NRestarts` must be exactly 0 and `bot-agent version` must match, or the `.prev` set is restored. Without that file they do not restart and print `not enrolled: agent not restarted`. `--runner-config` is copied into the installer's private directory before `policy check`, and that copy is what gets installed. A symlink, a non-regular file, or a file writable by group or other is refused. From v0.2.7, `install --runner` and `check --runner` also take `--project SLUG` (once), `--image PATTERN` (1 to 20), and `--enable`, not with `--runner-config`. The shell checks each value against the slug and pattern grammar before any file is written (exit 2 otherwise), then writes `enabled`, `projects`, and `images` to a file in the private directory, which takes the `--runner-config` path (policy check, `root:root` `0644`, `policy-owned`, hash in the record). With `--enable` the check must print `images=true`. An existing `runner.toml` is kept only when it is byte-identical; a different one exits 1 and nothing changes. A bundle path with a character outside letters, digits, and `. _ / + -` is refused before anything changes. The staged re-exec passes these flags on, and the operator's bundle path in `BOT_AGENT_INSTALL_BUNDLE`; the staged run checks that path against the same allowlist and that its `install.sh` is byte-identical to the staged copy. A successful `install`, including one that finds the host already installed, prints `next: sudo <bundle>/install.sh enroll --server '<server URL>'` before the summary, with ` --runner` when `--runner` was passed or the installer record already has the helper. `remove` stops `bot-agent-runner@*.service` instances before deleting the template. A failed stop or disable of the agent, the socket, a running helper instance, or an owned unit is reported, the files are still deleted, and the summary is `remove incomplete` (exit 1). No matching helper instance is not a failure. A runner socket unit that is not installed is not a failure. Workload removal matches the label `dev.deploybot.owner=bot-agent`. `--remove-workloads` fails if docker cannot list containers, volumes, or networks. On an enrolled host (`/etc/bot-agent/env` exists), `upgrade --runner` runs `systemctl enable --now bot-agent-runner.socket` after `daemon-reload` and before the agent restart, because the agent probes the helper only at startup. That verification also requires `systemctl is-active bot-agent-runner.socket` to be `active`. Rollback on an enrolled host re-enables the socket when the restored set includes it, after `daemon-reload` and before the restart. When the rollback removes the socket, it runs `systemctl disable --now bot-agent-runner.socket` before deleting that unit file. A host without the env file enables nothing. When there is no installer record but `/usr/local/bin/bot-agent` exists, `check` and `upgrade` print `installed: <version> (not installed by the installer)` from `bot-agent version` only when that file is a regular non-symlink executable owned by root and not writable by group or other; otherwise they report `installed: none`. The upgrade summary is `upgraded <old> -> <new>`. A managed directory that is a symlink (`/usr/local/bin`, `/etc/systemd/system`, `/etc/bot-agent`, `/var/lib/bot-agent-installer`, `/usr/local/libexec`, `/etc/tmpfiles.d`, the insecure-dev drop-in directory, or the host-files drop-in directory `bot-agent-runner@.service.d`) is refused instead of followed. `enroll` passes the join token to `bot-agent init` on stdin. `--insecure-dev` writes the same drop-in as `install --insecure-dev` and passes `BOT_AGENT_INSECURE_DEV=1` to `init`. An existing `insecure-dev.conf` still counts when the flag is absent. `init` stores a server URL whose path is empty or `/` with `/agent/v1/ws` appended, and keeps any other path. When the agent unit is active, `enroll` restarts it; otherwise it runs `systemctl enable --now bot-agent.service`, then enables the runner socket when `--runner` is set or the helper is already installed. It waits up to 30 seconds for a non-empty `BOT_AGENT_HOST_ID` and `BOT_AGENT_CREDENTIAL_ID` and for `BOT_AGENT_JOIN_TOKEN` to be absent, using the same trim, `export`, and unquote rules as the agent, and checking key names only. After the keys appear it runs `systemctl reset-failed` on `bot-agent.service`, waits the same 15 second settle as upgrade, and then requires the agent active with `NRestarts` exactly 0. It does not delete the env file. If that check fails, recovery is `systemctl stop bot-agent`, move `/etc/bot-agent/env` aside, then enroll again. Missing keys exit 1 with `enroll failed: credential not persisted`. Success prints `summary: enrolled`. A real upgrade, rollback, or enroll prints each systemd step it takes, matching the dry-run line without the `dry-run:` prefix (`systemctl enable --now bot-agent-runner.socket`, `systemctl restart bot-agent.service`, and `systemctl disable --now bot-agent-runner.socket` when that step runs), then `verify: active, NRestarts 0, version <v>` and, when this command enabled the socket, `verify: runner socket active`. From v0.2.12 `check_policy_file` runs the bundle's helper as `bot-agent-runner docker_check` (agent-protocol v1.17) and prints `docker: API <v> (ok)` (plus `; shared networks need Docker 25 (API 1.44)` below 1.44), `docker: API <v> (too old: …)`, `docker: not answering` or `docker: absent`; without the helper or a usable answer it falls back to `docker version` (`present` or `absent`). When the checked policy reports `images=true` or `edge=true` and Docker is not ok, `check` ends with `summary: check failed: <reason>` and exits 1; `install` and `upgrade` only print the line.

`/etc/bot-agent` is `root:bot-agent` mode `1770` (sticky). The agent can create its temp file and rename it over `env`. The sticky bit stops it unlinking the root-owned `runner.toml`. Mode `0700` owned by `bot-agent` would let the agent unlink that file. `install`, `upgrade`, and `rollback` set and verify `1770`. The installer never overwrites an existing `runner.toml` or env file. It does not stop or delete legacy `bot_agent` units.

`check`, `install` and `upgrade`, with the helper (`--runner`, or the helper already installed), refuse a policy that has programs on (`enabled = true`, a non-empty `run_as`, `max_programs > 0`) and `projects=0`, before any change (v1.12 item 7). `projects=0` comes from `policy check`; the other three keys are read from the file, which has already passed `policy check`, so each key is on one line.

`bot-agent policy check FILE` calls `policy.Check`, which is `Load` with ownership and mode skipped. `run_as` is still resolved against passwd and group. The installer checks `runner.toml` itself for mode `0644` and, outside the test hook, owner root. Output is `valid` plus effective flags, or `invalid: <reason>`. Reasons are the policy package's tokens (`parse`, `unknown_key`, and the rest). File bytes are not printed. `programs` follows `Enabled` when the file is valid. `images` follows `ImagesEnabled` (valid, enabled, both lists non-empty, no overlapping project names). `image_patterns` is the pattern count even when images are not enabled, so a file can be valid and still leave images off. After `projects_overlap=` it prints `shared_networks=<count>` and one `shared_network <name> <cidr> <slug,slug,…>` line per network in file order, `-` when it has no members (v1.13). Then `edge=<bool>` (v1.15), `host_files=<count>` and one `host_file <name> <path> <mode> <unit> <run_as> secret=<bool> health=<bool>` line per host file (v1.18); command lines are never printed. The installer matches its lines exactly, so the extra lines do not affect it; it reads the `host_file` lines to write the helper drop-in (below).

## Host config files (agent-protocol v1.18)

Spec: umbrella `docs/spec-host-config-files.md` (rev 1 with the rev 1a amendments in §10). An org admin edits a root-owned file of a unit Deploybot does not run (Defect Drainer's `/etc/dd-worker/policy.toml` and `secrets.env`). The helper checks it, swaps it in, restarts the unit, confirms it, and rolls back on its own. The threat model does not change: every writable path, owner, mode, unit, account and command comes from `runner.toml`; the server sends only a file name from that list and the bytes.

**Policy** (`internal/agent/policy/hostfiles.go`; shared vocabulary in `internal/agent/hostfiles`). Eight one-line string-array keys: `host_files = ["<name>=/etc/<dir>/<file>"]`; `host_file_modes`, `host_file_units`, `host_file_run_as`, `host_file_checks`, `host_file_health` and `host_file_idle` as `"<name>:<value>"`; and `host_file_secret` as a list of names. A syntax violation makes the whole file invalid with `parse`:
- name `^[a-z][a-z0-9-]{0,31}$`, at most 8 files, unique names and paths; every other entry names a declared file, once; modes, units, run_as and checks are required per file;
- path exactly `/etc/<dir>/<file>`, each component starting with a letter, digit or `_` (no dotfiles, so no host file can be another's candidate name). The dir is not `bot-agent`, `systemd`, `ssh`, `sudoers.d`, `pam.d`, `security`, `cron.d` or any `cron.*`, `polkit-1`, `apt`, `docker`, `caddy`, `postgresql`, `tmpfiles.d`, `sysusers.d`, `sysctl.d`, `modprobe.d`, `profile.d`, `ld.so.conf.d`, `logrotate.d`, `update-motd.d`, `udev`, `init.d`, `apparmor.d`, `dpkg`, `rsyslog.d` or `default`;
- mode `0600`, `0640` or `0644`; a secret file `0600` or `0640`;
- unit `^[a-zA-Z0-9][a-zA-Z0-9@._-]{0,127}\.service$`, not starting with `deploybot-`, `bot-agent`, `ssh`, `systemd-`, `dbus`, `docker`, `containerd`, `caddy`, `postgresql`, `networking`, `NetworkManager`, `tailscaled`, `cron`, `rsyslog`, `polkit`, `user@` or `getty`;
- run_as an existing account with uid and primary gid at least 100, primary group not `root`/`0` or `nogroup`, and not `nobody`, `bot-agent` or an account sharing `bot-agent`'s uid or primary gid (`hostFileRunAsOK`, spec A8; programs' `run_as` keeps the 1000 floor);
- a command is an absolute clean executable plus at most 16 arguments, split on single spaces (no shell, no quoting, no control characters); a health `--wait` must parse and be at most 165 s, so wait + 15 fits the 180 s settle maximum.

`policy.SafeExec` resolves an executable through symlinks (at most 16 hops). Every directory on the way to each link and to the target is root-owned and not group- or world-writable, each link is root-owned, and the target is a root-owned executable regular file that is not group- or world-writable. An unsafe or missing executable does **not** invalidate the policy (rev 1a A2): the loader sets `HostFile.ExecSafe` false, `policy check` adds ` exec=unsafe` to that file's line, and the helper refuses applies of that file with `forbidden_spec` stage `exec`. It checks at the start of each apply and again right before each command, so a link swapped during a DD upgrade is checked when it is used. Programs, images and the edge are not affected. An older agent refuses the keys as `unknown_key`.

**Hello and tasks** (`internal/agent/run/hostfile.go`).
- `hello.programs.host_files` is `[{"name","path","secret","unit","health"}]` from a valid policy, `[]` otherwise; never commands or content.
- Task kind `host_file_apply`, spec `{"name","content_b64","settle_sec"?,"force"?}` (content 1 to 65536 bytes, `settle_sec` 30 to 180): `forbidden` when the policy has no host files, `bad_spec` on a bad spec. The agent forwards the spec bytes to the helper verb `host_file_apply` with a fixed 600 s budget (`hostfiles.TaskTimeout`; the frame's `timeout_sec` does not change it) and zeroes the spec bytes when the task is done.
- Result: `succeeded` and `unchanged` are state `succeeded`; the other five outcomes are state `failed` with `error_code` the outcome. The payload is `{"outcome","stage","reason","took_ms"}`, plus `sha256` only on `succeeded` or `unchanged` of a non-secret file. The agent drops a secret file's hash itself, whatever the helper sent. A helper refusal (`bad_spec`, `policy_denied`, `io_error`) or a transport failure (`helper_unavailable`) is state `failed` with that `error_code` and a payload without `outcome`. A reply outside the allowlist (unknown outcome or stage, a reason other than a fixed token or `bad_[a-z0-9_]{1,64}`, an unknown field) becomes `helper_unavailable` and is never relayed.
- Status: at hello, after each apply and every 10 minutes the agent calls `host_file_status` (5 s) and sends `host_files_status {"files":[{"name","exists","owner_ok","reason"?,"matches_applied","size"?,"sha256"?}]}`. The 10-minute timer exists only when the policy has host files. `matches_applied` is null before the first apply (or when `.applied` is unreadable); `size` and `sha256` are only for a non-secret file, and the agent drops them for a secret one. Reasons: `missing`, `symlink`, `not_regular`, `owner`, `mode`, `nlink`, `dir`, `too_large`, `io_error`. A failed status call skips the frame.

**Helper apply** (`internal/runner/hostfile.go`, `hostfile_fs.go`), spec §2.3 with rev 1a:
1. Look up the name (`forbidden_spec` stage `lookup`, also for an invalid policy). Take `flock /run/bot-agent/hostfile-unit-<unit>.lock`: one apply per unit, so `dd-policy` and `dd-secrets` (both `dd-worker.service`) never interleave; a queued apply polls the lock with `LOCK_NB` every 100 ms and gives up (`io_error`) when its request is cancelled. It is not the helper-wide lock, so program verbs are not blocked. With the lock held the policy is loaded again and the name looked up again (a changed unit is `lookup`). Resolve `settle_sec`: default 60, raised to the health `--wait` + 15 when that is larger; a requested value below that is `forbidden_spec` stage `settle`. Check the executables (stage `exec`).
2. Open `/etc` and `/etc/<dir>` with `O_DIRECTORY|O_NOFOLLOW` (root-owned, not group- or world-writable) and the file through that handle: `fstatat` without following, then `openat O_NOFOLLOW|O_NONBLOCK` and `fstat` again. It must be a regular file (a FIFO is refused without blocking), owner root, group root or (for `0640`) the run_as group, exactly the policy mode, nlink 1, at most 64 KiB. Anything else, including a missing file, is `forbidden_spec` stage `target`. Deploybot never creates a host file or fixes its owner or mode.
3. Equal sha256: `unchanged`. Nothing is written to `/etc` and nothing restarts; the hash is recorded in `.applied`, so the first apply of today's bytes starts the history in sync.
4. Candidate `.<file>.deploybot-new` beside the target: a leftover file is unlinked (a directory there is `io_error`), then `O_CREAT|O_EXCL|O_NOFOLLOW`, owner root and the current group (a `0640` file keeps its run_as group), the policy mode set before the bytes, fsync. One deferred unlink removes any candidate the apply leaves.
5. Check as run_as with the candidate (opened by the helper) on stdin: exit 0 continues; exit 2 with exactly one stderr line `bad_[a-z0-9_]{1,64}` is `check_failed` with that reason; anything else (another exit, a timeout, two lines, more than 512 bytes of stderr) is `check_error`. 5b. Idle, unless `force`: exit 4 is `worker_busy`, any other failure `check_failed` `idle_error`. A request cancelled up to here stops the apply with no swap.
6. The current bytes go to `/var/lib/bot-agent-runner/host-files/<name>.prev` (root 0600, directory 0700).
7. `renameat` swaps, then the directory is fsynced. A failed fsync after the rename is logged (`dir_fsync_failed`) and the apply goes on, because the new bytes are in place. From the swap on, the apply runs on a context the agent's disconnect does not cancel.
8. `systemctl restart -- <unit>` (at most 60 s); the settle window starts when it returns. The health command must exit 0 within the window (its unit's `RuntimeMaxSec` and the helper's deadline are both the window). Without a health command, the unit must be `active` with an `InvocationID` right after the restart, and still `active` with the same id at the end of the window; each `systemctl show -- <unit>` has its own 10 s timeout.
9. On failure the previous bytes go back by the same candidate-and-rename path, and the unit is restarted and confirmed again: `rolled_back` with stage `restart` or `health` and the health reason (`not_connected`, `policy_invalid` or `not_running`, else `health_error`), or `rollback_failed` with stage `rollback` and the rollback's reason (or the first one when the rollback has none).
10. Success records the sha256 in `<name>.applied`. When `.applied` cannot be written (after `succeeded` or `unchanged`), the outcome stays and the helper logs `applied_record_failed`; status then shows the file as not matching until the next apply.

Budgets (rev 1a A4): check 15 s and idle 10 s, each plus a 5 s kill grace; restart 60 s; settle up to 180 s; the same again for a rollback. The worst case is 515 s, under the 600 s task timeout (`TestHostFileWorstCaseBudget`). The API waits 610 s.

Stderr is read up to 513 bytes and nothing but the token is kept. The helper logs one line per apply: name, outcome, stage and reason. `host_file_status` waits for no lock, so it never queues behind an apply. When it finds a leftover candidate and the unit lock is free, it removes it and logs `leftover_candidate_removed`; a directory at that name is left and logged.

**Running as run_as.** No setuid in the helper: `systemd-run --wait --pipe --collect --quiet --uid=<uid> --gid=<gid>` with numeric ids from passwd, then `-p` for each of `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, `PrivateNetwork=yes`, `PrivateDevices=yes`, `ProtectKernelTunables=yes`, `ProtectKernelModules=yes`, `ProtectControlGroups=yes`, `RestrictSUIDSGID=yes`, `LockPersonality=yes`, `LimitCORE=0`, `TimeoutStopSec=2`, `MemoryMax=256M`, `TasksMax=64`, `ProtectProc=invisible`, `ProcSubset=pid`, `InaccessiblePaths=-/run/docker.sock -/var/run/docker.sock -/run/containerd/containerd.sock -/run/podman/podman.sock` and `RuntimeMaxSec=<budget>`, then `--unit=deploybot-hostfile-check-<name>-<16 hex> -- <argv>`. The environment is fixed (`LANG=C`, `PATH=/usr/bin:/bin`), stdout is discarded, and `WaitDelay` is 2 s. The exec is `Sys.RunUnit`; the tests fake it, and `TestRunUnitRealExec` runs the production function against a stub `systemd-run`. That the candidate reaches the check byte for byte through `--pipe`, and that the sandbox holds, is the pi3 live check (spec §5 items 9 and 14).

**Installer.** `install|upgrade --runner` (also when the version is unchanged, and as a plan in the dry run) writes `/etc/systemd/system/bot-agent-runner@.service.d/host-files.conf`, with one `ReadWritePaths=-/etc/<dir>` per distinct directory of the `host_file` lines of `policy check`, then `daemon-reload`. It removes the file and the empty directory when there are no host files, and leaves a matching file alone. Rerunning `upgrade --runner` repairs a drop-in that a failed run or a hand edit left wrong. `check --runner` prints `host files: <n>; drop-in …: in sync`, `missing`, `differs` or `present but not needed`, and the directories. `remove` deletes it. A symlinked drop-in directory is refused. The drop-in is not in the installer record, so `rollback` leaves it; it only lets the helper write directories the policy names.

**Test helper.** `cmd/hostfile-testhelper` builds only with `-tags hostfile_testhelper` and is in no bundle (`TestHostfileTesthelperNotShipped`). It is a stand-in worker for the pi3 live check:
- `policy|secrets check --file -` follows the exit 0/2 contract, driven by a `testhelper_check = "…"` line;
- `probe` exits 2 with `bad_u<uid>_w<0|1>_n<0|1>` (whether it could create a file in `testhelper_probe_dir`, default `/etc/hostfile-test`, and connect to `testhelper_probe_addr`, default `1.1.1.1:443`);
- `--report` logs the stdin sha256 and size to syslog (`journalctl -t hostfile-testhelper`), and `--report-reason` returns them as `bad_n<bytes>_<52 hex>`;
- `health --wait <dur>` and `health --idle` read `health=` and `idle=` lines from a status file (default `/var/lib/hostfile-test/status`);
- `serve` is the stand-in unit's ExecStart.

## Agent upgrade from the server (agent-protocol v1.20)

Spec: umbrella `docs/spec-agent-self-upgrade.md` (rev 1, §12 contract notes). An org owner or admin upgrades a host's agent from the console or MCP; the host rolls back by itself if the new agent does not come back.

Threat model. The server names only a version. Everything else is fixed on the host: the opt-in (`agent_upgrade = true` in the root-owned `runner.toml`, off by default and never written by the installer), the download address (`https://github.com/more-than-code/bot-agent/releases/download/v<version>/`, with redirects only to `github.com`, `objects.githubusercontent.com` and `release-assets.githubusercontent.com`), the check (an Ed25519 signature over `SHA256SUMS`, verified with the public key compiled into the helper, `internal/release`), and the command (the bundle's own `install.sh upgrade`). A compromised API or GitHub account cannot get its own binary run, because neither holds the private key; it stays offline on the signer's machine and `go run ./cmd/release-sign` (never shipped) makes `SHA256SUMS.sig`. A build with the placeholder key (all zero bytes) refuses every bundle. The work runs in a transient root unit, not in the helper: the helper keeps `RestrictAddressFamilies=AF_UNIX` and its read-only `/usr/local`, and the unit outlives the agent restart that the upgrade causes. Nothing from the request reaches that unit's command line except the version, which must match `^[0-9]{1,4}\.[0-9]{1,4}\.[0-9]{1,4}$` and be newer than the installer record's `version` line. The agent stays unprivileged.

**Policy and hello.** `agent_upgrade` is a bool key (`policy.AgentUpgradeEnabled`: a valid file with the key true; it does not depend on `enabled`). `policy check` prints `agent_upgrade=<bool>` after the host_file lines. `hello.programs.agent_upgrade` carries the flag; top-level `hello.last_upgrade` is the helper's result file (`{"version","outcome","reason","at"}` or null), read once at agent start through the helper verb `agent_upgrade_result`, and only when the host opted in. `agent_upgrade_https_proxy` (one quoted string, `http(s)://host:port`, no userinfo, path, query or fragment, at most 256 bytes, else the file is invalid with `parse`) is the only proxy the download uses; `policy check` prints `agent_upgrade_https_proxy=<set|unset>`.

**Task.** Kind `agent_upgrade`, spec `{"version":"X.Y.Z"}`: `forbidden` when the hello flag was false, `bad_spec` for another shape. The agent forwards it to the helper verb `agent_upgrade` with the frame's `timeout_sec` capped at 120 s (120 s when unset; the generic 60 s clamp does not apply). Success is state `succeeded` with `{"state":"accepted"}`; a helper refusal is state `failed` with `policy_denied`, `busy`, `not_newer` or `bad_spec`, anything else `helper_unavailable`. On an opted-in host the agent polls `agent_upgrade_result` every 10 s for up to 15 minutes at start and again after an accepted task (which restarts the window): the result file is written after the installer finishes, so the new or restored agent usually starts before it exists. It sends `agent_upgrade_result {"result":…}` whenever the helper's result differs from the last one this process sent or put in hello, and stops early once the helper reports no upgrade running and a new result has been sent. The helper's reply carries `running` (agent and helper ship together; not an API field). A later hello carries the same result in `last_upgrade`.

**Helper verb `agent_upgrade`** (`internal/runner/agentupgrade.go`), checks in order: policy (`policy_denied`); version format and newer than the record (`bad_spec`, `not_newer`; a missing record is `not_newer`); the helper-wide lock taken without waiting, every other lock in `/run/bot-agent` (image, edge, host-file, upgrade) free, `bot-agent-upgrade.service` not active, activating or deactivating, and no cool-down (a result for the same version, not `succeeded`, under 10 minutes old by its `at`) (`busy`). The host checks "newer and signed" only; "latest" is the server's rule. The unit name starts with `bot-agent`, which no program unit (`deploybot-*`) and no host-file unit can use. Then `systemd-run --unit=bot-agent-upgrade --collect --property=RuntimeMaxSec=900 --property=TimeoutStopSec=150 --property=KillMode=mixed /usr/local/libexec/bot-agent-runner upgrade-run <version>` and `accepted`.

**`bot-agent-runner upgrade-run <version>`** (`internal/upgrade`), as root in that unit:
0. Take `flock /run/bot-agent/upgrade.lock` without waiting and hold it to the end (a second run stops without a result). While it is held, the helper's mutating verbs (program start/stop/restart, the image mutations, `edge.apply`, `edge.stop`, `host_file_apply`) answer `busy` in their own reply shape, and `agent_upgrade_result` reports `running`.
1. Download `SHA256SUMS` and `SHA256SUMS.sig`, verify the signature (`signature_invalid`), and only then `bot-agent-v<version>.tar.gz`: HTTPS only, allowed hosts on port 443 without userinfo (also after each redirect), at most 5 redirects, 64 MiB and 120 s per file. The only proxy is `agent_upgrade_https_proxy` from `runner.toml` (no `NO_PROXY`); nothing is read from `/etc/bot-agent/env`, which the agent can write. Failure: `download_failed`.
3. Unpack into `/var/lib/bot-agent-runner/upgrade/<version>/` (0700; files 0600, or 0700 with an execute bit): regular files and directories only, all under `bot-agent-v<version>/`, no absolute path, `.` or `..` segment, or link, at most 1000 entries, 256 MiB of files, and 257 MiB of decompressed stream (headers included). The bundled `SHA256SUMS` must equal the signed one byte for byte and list `install.sh` and the four `units/*` files; every listed file must match and no other regular file may be in the tree (`bundle_invalid`). The bundled `bot-agent-v<version>-linux-<GOARCH>` must print the version (`version_mismatch`).
4. Run `/bin/sh <bundle>/install.sh upgrade` (plus `--runner` when the record lists `/usr/local/libexec/bot-agent-runner`) with `BOT_AGENT_INSTALL_BUNDLE=<bundle>` and a fixed PATH. Exit 0 is `succeeded`. Output with `upgrade failed, restored` (a restore whose verify passed) is `rolled_back`, with `not_reconnected` when it also has `verify: no hello after restart` and `install_failed` otherwise. Anything else, including `rollback verify failed`, is `failed` `install_failed`. When the unit is stopped, the context is cancelled and install.sh gets SIGTERM (`cmd.Cancel`) and 120 s (`WaitDelay`) to run its EXIT-trap rollback before a kill; the outcome is then `failed` `install_failed`. Note that systemd also sends SIGTERM to the whole unit and its default `TimeoutStopSec` (90 s) bounds the grace in practice.
5. Write `result.json` (0600, atomic) and remove every other staged version directory. The helper reads `result.json` and the installer record with a 64 KiB cap.

**Installer marker.** The agent touches `<state dir>/last_hello` (0600, its own file) after every acknowledged hello. `verify_active_version` touches `/var/lib/bot-agent-installer/hello-ref` before the restart and, after the settle sleep, waits up to 90 s for `last_hello` in the agent's state directory (`BOT_AGENT_STATE_DIR` from `/etc/bot-agent/env`, parsed without evaluation, else `/var/lib/bot-agent`; a value that is not a plain absolute path fails the verify) to be newer (`find -newer`); otherwise it prints `verify: no hello after restart` and fails, so the existing rollback runs. A rollback's verify (automatic or `install.sh rollback`) keeps the old checks (active, `NRestarts` 0, version) and does not wait for the marker: an agent before 0.2.15 never writes it, and with the server down the restored agent cannot say hello. Only an enrolled host restarts and waits. `BOT_AGENT_INSTALLER_HELLO_WAIT` changes the 90 s in test mode only.
