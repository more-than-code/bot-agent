**Cross-repo design (the source of truth for the protocol, permissions, and schema):** [../../docs/design-bot-agent-deploy.md](../../docs/design-bot-agent-deploy.md). This file covers only what lives inside this repo.

## Process model

- One static Go binary, `linux/arm64` (Pis) and `linux/amd64` (grok-bot-box). It is deterministic and runs no LLM.
- It opens no listen socket of any kind. Its only network peers are bot-api-server (outbound `wss://`) and, for probes, `127.0.0.1:<exposed port>`.
- It refuses to start if: euid is 0; `BOT_AGENT_SERVER_URL` is not `wss://`; the env file mode is not 0600; or, in phase 2, `DOCKER_HOST` is empty, `tcp://`, or the raw engine socket.
- `bot-agent version` prints the version. There is no `env` subcommand and nothing else prints configuration.

## Configuration

`/etc/bot-agent/env` (mode 0600, owner `bot-agent`, directory 1770 sticky `root:bot-agent`):

```
BOT_AGENT_SERVER_URL=wss://<api-host>/agent/v1/ws
BOT_AGENT_JOIN_TOKEN=<one-time; removed after enroll>
BOT_AGENT_HOST_ID=<written on enroll>
BOT_AGENT_CREDENTIAL_ID=<written on enroll>
BOT_AGENT_CREDENTIAL=<written on enroll; rotated by the server>
```

Rewrites are atomic: temp file in the same directory, mode 0600, fsync, rename. The directory is sticky so the agent can rename that temp file over `env` and cannot unlink the root-owned `runner.toml`. Collection intervals and health checks come from the server in `hello_ok.config`. The agent clamps them (host metrics 5–60 s, processes and health 30–300 s, at most 50 checks).

## Phase 1: read-only

| Area | What | Matches Telegraf today |
|---|---|---|
| Host compute | cpu (`cpu-total`, `usage_idle`, …), mem, disk (`/`), diskio (whole disks), net (no `lo`), system (load1/5/15, uptime), temp (`cpu_thermal` where present) | Same names and units as `docs/api-contract.md`, so the overlap comparison is like for like. |
| Processes | Top 20 by cpu and top 20 by RSS each interval, plus every process of a known service. Irix cpu (100 = one core). The agent truncates `cmdline` to 1024 characters and redacts secrets (agent-protocol §Redaction, `internal/agent/redact`) before sending; the server redacts again on ingest and shortens it for display. | procstat scan + topk |
| Services | Discovery: listening TCP sockets → pid → systemd unit (via `/proc/<pid>/cgroup`) or process. Reported in `hello`, when they change, and at least every 5 minutes while connected; see agent-protocol v1.2. | `services/*.json` (hand-written) |
| Health | `probe_health` per configured check: `http://127.0.0.1:<port><path>` or a TCP connect. The port must be one the service is listening on (D12). No redirects; timeout ≤ 10 s; body not stored, only status, latency, and result. | `inputs.http_response` |
| Live tasks | `host_snapshot`, `probe_health` | — |

A services report is the host's full set, so the agent sends one only from a complete discovery: the process scan succeeded and, when the program policy is enabled, the helper's owned-program lookup succeeded and, when images are enabled, `container_list` succeeded. If any of those fail, that cycle sends no `services` frame and the previous report stays. `hello` includes `services_complete`, which is false with `services` empty when the first discovery did not finish, so the server does not store that hello as the full set (agent-protocol v1.3.2).

The user-scope systemd caveat from spec-v1 still applies: a system user cannot read another user's bus. Units are inferred from the cgroup path, which needs no bus.

## Phase 2: logs, deploy, run/stop

The Docker socket proxy below is superseded by agent-protocol v1.4: `bot-agent-runner` opens `/var/run/docker.sock` itself. See Images.

- **Docker socket proxy:** a separate unit, the only process that opens the engine socket (raw socket access is root-equivalent). It listens on `/run/bot-agent/docker.sock` (mode 0600, owner `bot-agent`). Allowed calls:
  - `GET /containers/json`, `GET /containers/{id}/json`, `GET /containers/{id}/logs`;
  - `POST /containers/{id}/start`, `POST /containers/{id}/stop`;
  - `GET /images/{name}/json`, `POST /images/create` (pull, no registry auth);
  - `POST /containers/create`, only after the body is validated. It rejects `Privileged`, `CapAdd`, `Devices`, `Binds`, bind-type `Mounts`, `NetworkMode=host`, `PidMode=host`, `IpcMode=host`, `UsernsMode=host`, and `User` 0/root. It requires the label `dev.deploybot.owner=bot-agent`.

  - *For redeploy (umbrella §5.3, D30):* `POST /containers/{id}/rename` and `DELETE /containers/{id}` (never `v=1`), only for containers labelled `dev.deploybot.owner=bot-agent`.

  Everything else is denied: build, exec, attach, kill, commit, volumes and networks endpoints, and swarm. Body validation is why a small custom proxy is recommended (umbrella D26).
- **Owned list:** `/var/lib/bot-agent/owned` (mode 0600), one container name per line. Only a successful `deploy` adds a name and only undeploy removes one. `logs`, `run`, and `stop` refuse names that are not on it (`not_owned`), whatever the server says.
- `deploy`: if a container with `container_name` exists, adopt it (owned list only; the container is untouched). Otherwise pull the image if needed, create the container from the closed spec (umbrella §5.2), start it, and add it to the list.
- `redeploy` (umbrella §5.3, D30): created containers only. Pull first, stop and rename to `<name>-prev`, create and start the new container, wait for health, and on failure roll back to `-prev`.
- Secrets (umbrella §5.4, D31): values arrive only inside a deploy/redeploy task frame as `secret_env`. They go straight into the Docker create body. They are never written to `tasks/`, the spool, or the journal, and are redacted by exact value from logs and results. `status` results never include `Config.Env`.
- `logs`: tail 1–1000 lines, stdout/stderr flags, no follow. Redacted with the shared regex and capped at 64 KiB. Viewers may request it (umbrella D19).
- One mutating task per service at a time. Task files are kept under `/var/lib/bot-agent/tasks/<task_id>.json` so a result survives a reconnect. A mutating task that was not finished when the process restarted is reported `failed`/`agent_restarted` and is not re-run.

## Every task, before running

1. `host_id` matches the enrolled host.
2. `expires_at` has not passed (clock corrected by the `hello_ok.server_time` offset).
3. `kind` is in this phase's allowlist and in the build's capabilities.
4. The service is known; for logs/run/stop it is also owned.
5. `spec` keys are from that kind's closed set.

Image tasks add four checks after the host, expiry, kind, and closed-key checks, in this order: the policy is valid and images are enabled (`policy_denied`); `project` is in `projects` (`policy_denied`); ImageSpec and entry field rules (`bad_spec`); the image matches an `images` pattern (`policy_denied`). A non-null `service` is `bad_spec` before the policy check. The frame's `timeout_sec` is the deadline for the whole image sequence, clamped to at most 4020 seconds. Zero or negative uses 15 seconds. Program tasks keep the 15–60 second cap.

## systemd unit (sketch; Joe installs)

The v1 hardening carries over ([v1 §10](../../docs/design-bot-agent-deploy.v1.md)): `User=bot-agent`, no supplementary groups, `NoNewPrivileges`, `ProtectSystem=strict`, `ReadWritePaths=/var/lib/bot-agent /etc/bot-agent`, empty `CapabilityBoundingSet=`, `InaccessiblePaths=-/run/docker.sock -/var/run/docker.sock -/var/lib/bot-agent-runner` (the leading `-` lets a host without that path start), and `EnvironmentFile=/etc/bot-agent/env` (no leading `-`). Phase 1 additionally needs read access to `/proc` (for other users' processes: `ProtectProc=default`, not `invisible`) and to `/sys/class/thermal`. Unit `bot-agent.service`, binary `/usr/local/bin/bot-agent` (accepted). The legacy `bot_agent.service` and `/usr/local/bin/bot_agent` are removed by Joe on pi2, pi3, and pi4 after the new agent is up (umbrella D24). The agent's installer never touches them.

bot-agent replaces Telegraf completely (umbrella D23). After a host's overlap ends, Joe removes Telegraf there.

grok-bot-box has no systemd. It starts from a script that Joe reruns after every restart or wake, replacing `grokbox-metrics-start` (umbrella D27).

## Programs (v1.3)

Wave 1 of `docs/spec-project-catalog.md`, amended by agent-protocol v1.3.1 and v1.5.1, is a root helper, not a capability on `bot-agent.service`. `cmd/bot-agent-runner` is installed at `/usr/local/libexec/bot-agent-runner` (`root:root`, `0755`). systemd accepts `/run/bot-agent-runner.sock` and starts one `serve-conn` process per connection. The agent dials that socket. The connect budget is 5 seconds. The rest of the call uses the task timeout (`timeout_sec`, clamped to 15–60 seconds); hello and discovery keep a 5 second limit. It does not resolve paths under `/home`. The helper re-validates the root-owned policy and the task, including realpath and exec resolution, writes `/etc/systemd/system/deploybot-<project>-<entry>.service` (`root`, `0644`, with `[Install]` / `WantedBy=multi-user.target`), `/var/lib/bot-agent-runner/programs/<unit>.env` (`root`, `0600`), and the same request at `/var/lib/bot-agent-runner/programs/<unit>.json` (`root`, `0600`). The `programs` directory is `0700`. The unit's `EnvironmentFile=` is that env path. `start` writes the env file, then the spec, then the unit, then runs `daemon-reload`, `enable`, and `restart`, so a program that was running is started again at boot. A `\` in the directory, the executable, or the `run_as` home is `policy_denied` before any write. A drop-in at `/etc/systemd/system/<unit>.d` or `/run/systemd/system/<unit>.d` (any type) is `io_error` before `enable` on `start` and `restart`. The helper never creates or removes a drop-in. A `restart` of a unit already in `/etc` does not rewrite it, and still runs `daemon-reload`, `enable`, and `restart`. `stop` runs `disable`, `stop`, then removes every regular file it owns among the unit, env, and spec, including an owned `/run` copy. It keeps going when one cannot be removed, never unlinks a symlink, runs `daemon-reload`, and replies `io_error` if a file it tried to remove remains. A later stop with no unit file removes a leftover spec whose stored project and entry match. Otherwise a stopped program leaves nothing behind. `packaging/tmpfiles.d/bot-agent-runner.conf` still creates `/run/bot-agent` and `/run/bot-agent/env` at boot (`0700` `root:root`); the helper creates them too, because the lock, the image locks, and a not-yet-migrated env file live there. A start whose `daemon-reload` or `enable` fails, or whose unit does not become freshly active, disables and stops that unit, removes the `/etc` files and an owned `/run` copy, runs `daemon-reload` after those files are gone, and is `start_failed`. If that cleanup cannot remove a file, or `disable` fails, the reply is `io_error`. If `daemon-reload` fails while `restart` is moving a unit off `/run`, the helper removes the `/etc` files it just wrote and keeps the `/run` files, with no second reload. If `enable` fails after that reload, it removes those files and runs `daemon-reload` again so the `/run` unit is loaded. Both are `start_failed` with `fresh` false. A failure after `enable`, or a failure of a unit already in `/etc`, keeps the `/etc` unit enabled. `max_programs` counts unit files, not only active units. A name in both `/etc/systemd/system` and `/run/systemd/system` counts once. `status`, `logs`, `sockets`, and `list` look in `/etc` first, then `/run`. Restart re-checks the stored request against the current policy and stops a unit that is no longer allowed. The next `start` of a unit this helper still owns under `/run` writes the `/etc` copy and removes the `/run` unit and `/run/bot-agent/env/<unit>.{env,json}` in that same verb. `restart` writes that `/etc` copy only when it is missing and removes the `/run` files only after `enable` succeeds. `stop` removes an owned `/run` copy together with the `/etc` files. The helper refuses a foreign file in `/etc` with `not_created` whatever is in `/run`, and that owned `/run` unit still counts for `max_programs`. `list` does not return it. Our unit in `/etc` wins over a foreign same-name file in `/run`: the verb acts on `/etc` and leaves the `/run` file untouched. `bot-agent-runner@.service` `ReadWritePaths=` includes `/etc/systemd/system` so the helper can install those units; `bot-agent.service` is unchanged and already hides `/var/lib/bot-agent-runner`. Tests drive systemd, journalctl, and the socket through fakes. See `NOTES.md` for what still has to be confirmed on pi1.

Threat model, from the catalog spec: a compromised API cannot change `/etc/bot-agent/runner.toml`; a compromised agent stays unprivileged and cannot exceed that file, because the helper checks every request again and the peer uid must be `bot-agent`. Polkit can constrain unit names and still let a transient unit run as root, which is why the helper is the privileged step. There is no shell unless `allow_shell` is true. Env values are not logged. `bot-agent.service` gains no capability. `ProtectHome=read-only` on a program unit leaves other homes readable, and an allowlisted interpreter runs the caller's arguments as `run_as`. Both follow from the host owner choosing `run_as` and `exec_allow`.

Rollback is local. Set `enabled = false` and restart the agent, or `systemctl disable --now bot-agent-runner.socket`. New tasks stop. Units already enabled keep running, and an enabled unit comes back at the next boot, until an administrator runs `systemctl disable --now 'deploybot-*'` and removes the unit, env, and spec files. Disabling only the helper does not disable those units. The agent reads the policy only at startup, so `enabled = false` does not take effect until that restart. After that it no longer reports those units as owned services, and it will not stop them itself.

## Images (agent-protocol v1.4)

`internal/agent/images` is the shared vocabulary. `internal/runner` owns the Engine client and the verbs. The agent does not import `internal/runner`. It calls the ten image verbs through the existing helper client in `internal/agent/run`.

Agent task kinds are `image_deploy`, `image_rollback`, `image_remove`, `image_start`, `image_stop`, `image_restart`, `image_status`, and `image_logs`. Specs use the v1.4 closed key sets. `hello.programs.images` follows `ImagesEnabled` (valid, enabled, both lists non-empty, and no listed project is another plus `-` plus more characters). `hello.programs.docker` is the first `container_list` of the process: success latches true, failure latches false. `hello.programs.files` is true whenever `programs` is sent. `hello.programs.docker_health`, `hello.programs.healthcheck`, `hello.programs.logging`, and `hello.programs.health_policy` are true the same way. The agent calls `container_list` only when images are enabled, including when the scan or the program lookup already failed, and it merges containers only when that cycle is still complete.

Service deploy is `image_pull`, then `container_status`. Running this digest with this `spec_hash`, this `files_hash`, and `force` false is `unchanged`. When the spec has a `healthcheck`, `unchanged` also requires that container's `container_list` health to be `healthy`. The agent computes `files_hash` from the task's files; it is empty when there are none. Otherwise `container_deploy`, then a health wait: the entry's configured `http` or `tcp` checks on `127.0.0.1` when the port is one of the spec's host ports, or else `running` with `restart_count` 0 for `healthy_after_sec`, polled every 2 seconds. A service whose spec has `healthcheck` polls `container_list` every 2 seconds instead, until `health` is `healthy` and those checks pass. `starting` keeps waiting. `unhealthy`, or the limit `max(timeout_sec, start_period_sec + interval_sec × (retries + 1))`, calls `container_rollback` only when the container before this deploy was `running`, and otherwise stops the new container and reports `failed`. That `timeout_sec` is the task frame timeout. `image_rollback` uses the same wait. Without `healthcheck` the wait is unchanged. A failed wait calls `container_rollback` and finishes `rolled_back` or `rollback_failed` only when the container before this deploy was `running`. Any other state stops the new container and reports `failed`, and a parked container stays on `-prev`. A `container_status` error during that wait, including `docker_unavailable`, is `failed` and does not roll back. A job pulls, removes a container that is present, deploys, and polls every 2 seconds until `exited` or the spec `timeout_sec` (10..3600). Exit 0 is `succeeded`; any other exit is `failed` with `exit_code`; the deadline stops the container and the outcome is `timeout`. Cancelling the task context is `failed` and does not stop the container. An image task spec may be as large as the 1 MiB agent frame. Image helper verbs accept up to 2 MiB. Program verbs stay at 64 KiB. A helper body over its verb's limit is outcome `failed`. A service `image_rollback` whose digest equals the kept container (`container_status.prev.digest`) swaps that container back with `container_rollback` and does not pull. Healthy is `succeeded` with that digest; not healthy is `failed`. When the spec has `healthcheck`, that wait is the `container_list` wait. Other digests still pull `<name>@<digest>` and deploy. Job rollbacks stay on the pull path. The other kinds are one verb each. `task_result.status` is `succeeded` only for `succeeded` and `unchanged`; otherwise it is `failed` and `error_code` is the outcome. Helper refusals `{"error":...}` and transport refusals `{"ok":false,"reason":...}` both map: `image_unavailable` and `conflict` stay, `policy_denied` and `bad_spec` become `forbidden_spec`, and `docker_unavailable` or a transport error becomes `failed`.

Health failure policy (agent-protocol v1.9, spec `docs/spec-health-policy.md`). `images.ImageSpec.HealthPolicy` holds the optional keys as pointers, so an explicit `0` or `""` is refused instead of defaulted; `Health()` fills `rollback`, `none`, 45, 3. `Validate` refuses unknown keys (strict decode), bad enums, out-of-range numbers, the key on a job, an `on_unhealthy` action without the entry's `healthcheck`, and `keep` with an `on_unhealthy` action (rev 2), in the agent and again in the helper. `deployService` reads `on_deploy_failure` only for `image_deploy`: `rollback` is the v1.6.1 path unchanged, `stop` calls `container_stop` whatever the pre-deploy state, and `keep` leaves the new container running; both report `failed` with the current status and tail. The helper adds the three `dev.deploybot.on_unhealthy`/`unhealthy_after_sec`/`max_actions_per_hour` labels at create when `on_unhealthy` is not `none`, and `container_list` returns them as `policy` for rows with the owner label (`images.PolicyFromLabels`; an invalid value is null). `keepLabels` is unchanged, so the policy labels are not in `labels`. The supervisor (`internal/agent/run/supervise.go`) runs from `Run` when images are enabled, every `Options.SuperviseEvery` (15 s). Each poll lists containers; a failed list ends every unhealthy streak. It considers owned current containers (name `<project>-<entry>`, host label, project allowed) with a non-`none` policy, and only `running` + `unhealthy` ones extend a streak. The per-entry lock (`entryLock`) is a shared/exclusive lock with a cancellable shared side: every image task takes the shared side for its whole run, waiting for a running supervisor action only within its task context (on timeout it is `failed` and calls no helper verb), so tasks are not serialised against each other; the supervisor only tries the exclusive side, so it never waits and never acts during a task. The supervisor does nothing when `machineHost()` is empty (unreadable machine-id), and the host label must match. Under that lock it checks the threshold, the sliding one-hour action window, and for `rollback` the once-per-deploy flag and a listed `-prev` (the `<project>-<entry>-prev` name with the same owner, project, entry and host labels; a name squatter counts as no `-prev`); a block marks the entry `gave_up` once. `image_deploy` and `image_rollback` clear the entry's state when they finish, before releasing the lock. Actions are `container_restart` or `container_rollback` with a 60 s context, longer than the helper's 30 s stop grace (`images.StopGraceSec`), then a `container_status` read with its own 5 s context (65 s budget, rev 3); a failed call still counts, reports `result` `error` with a null digest, and skips the status read. Otherwise the digest is the running container's after the action; when that read fails or has no digest, it is the digest the poll already knew (the current container for restart, the listed `-prev` for rollback), or null when none was listed. `gave_up` sends the listed current digest. Frames go to an in-memory queue (cap 100, oldest dropped) that the session sends after `replay` on each connection and whenever the queue wakes the loop; `auto_action_ack` removes a frame. Nothing is persisted: counters and unsent frames are lost on agent restart.

Discovery names an owned container (four labels, host label, project in `projects`) exactly by its entry, with `owner.kind` `image`. A non-owned row that collides is renamed. An owned row that already has the name keeps it, and the extra container is omitted rather than suffixed. The host label is `images.HostID` of `/etc/machine-id` when that file is readable under the agent sandbox. If it is not, any non-empty host label is accepted and the agent logs that once, without the path. The `-prev` slot is not a second discovered service; its host ports are still dropped from the unmapped list, and a lone `-prev` container is the owned service. Every other container is `kind` `container`, named by the container name without one leading `/`, with `image_digest` null and `"owner":null`. `image_digest` is present on every discovered row. Published host ports are not also reported as unmapped listeners. `container_list` returns at most 200 containers, Deploybot-labelled rows first, with `truncated` set when it cut. A truncated list is still a complete discovery, and the agent logs that once. Each item's `health` is `healthy`, `unhealthy`, `starting`, or null. While `config.docker_health` is true, a complete pass emits one Docker `health` sample for each container service that is `healthy` or `unhealthy`. `starting` and null emit nothing.

Env values, `registry_auth.token`, and file contents live only for the task. They are not logged. The spec bytes are zeroed when the task returns, and the pending result has no env object and no file content. Exact-value redaction (`internal/agent/redact`) replaces the registry token and the secret-file values from v1.5 with `[REDACTED]` (the whole content when it is 6–4096 bytes, trimmed lines of 16–4096 bytes, and JSON string values and their lines in that same line range). When `secret_keys` is absent, every env value of at least 6 bytes is included too. When `secret_keys` is present, only those env values are included, and a key that is not in `env` is `bad_spec`. Deploybot replaces an env secret with its preview: the first four runes and `…` when the value has at least 16 runes, otherwise `••••`. Forms are the raw bytes, base64 standard and URL (padded and raw), and both JSON-escaped forms, before the v1.0.1 regex, and this applies only to that task's result strings and log lines. `outcome`, `digest`, `exit_code`, and status fields are passed through as the helper returned them. Deploy and rollback tails send the token and file pieces on `container_logs` `redact` and the env values on `redact_env`. Each list is clipped to 2048 values, 6–4096 bytes each, and 512 KiB. The helper applies them to each raw line before the regex and the 2048-character cut, and does not log or return either list. `image_logs` sends neither list. This is best-effort. It is not a secrecy boundary (spec §3.4 and §12.9): the agent sees the values, and a container can print them in another encoding or send them over the network.

The helper talks to Docker Engine `/v1.47` on `/var/run/docker.sock` with a small client of fixed methods. A deploy whose spec has `healthcheck` sends Engine `Healthcheck`: `Test` is `CMD` plus the argv, and `Interval`, `Timeout`, and `StartPeriod` are nanoseconds. The key is absent when the spec has no `healthcheck`, so the image default stands. List rows read `Health.Status` when that object is present (API v1.52); otherwise they read the `Status` suffix `(healthy)`, `(unhealthy)`, or `(health: starting)`. URL path segments are escaped. Containers are addressed by the id from the helper's own name lookup. Query strings are built from typed values. Response bodies are size-capped. Tests use a fake Engine on a unix socket. There is no Docker SDK and no real Docker in the unit tests. Stop uses `t=images.StopGraceSec` (30). `container_restart` and `container_rollback` of a running container run every step from the stop on under `finishCtx`, which is `context.WithoutCancel` of the verb context bounded by `finishBudget` (60 s), so a caller that gives up (the socket-close watcher cancels the verb context) cannot leave the container stopped (agent-protocol v1.9 rev 3). Restart starts the container after the stop, even if the stop failed (starting a running container is a no-op). Every deploy (service or job), rollback and remove reads its pair through `loadPairClearing`. From the same list, it first removes a leftover `<name>-old` that passes `images.OwnsLabels` for the entry, together with its `.new` slot, and leaves it out of the `max_containers` count. A container on that name with other labels makes the verb return `conflict` and is not touched (rev 3b). A rollback of a running container (`rollbackRunning`) then, on `finishCtx`, it stops the original, renames it to `<name>-old`, moves its slot to `<name>.new` and `-prev`'s slot to the current name, renames `-prev` to the current name, and starts it. Only then does it remove the original and the `.new` slot. On any failure `restoreOriginal` runs on a fresh 20 s `recoverCtx` that is not derived from `finishCtx`; the restart's start after its stop uses one too. It lists containers (a failed rename may have landed; without a list it renames blind), puts `-prev` and the original back on their names, undoes exactly the slot moves that happened, and starts the original by id. Slot-restore failures, and a failed final remove of `-old` after `-prev` started, are logged; the latter rollback still succeeds. The verb still returns the refusal. A rollback of a non-running container keeps the previous remove-then-swap path. Deploybot sets `HostConfig.LogConfig` on every container create to the json-file driver with `max-size` and `max-file` (10m and 3 unless ImageSpec `logging` is set), and `hello.programs.logging` is true.

`bot-agent-runner@.service` sets `RuntimeMaxSec=900` and adds `/var/run/docker.sock` to `ReadWritePaths`. It also sets `StateDirectory=bot-agent-runner` and `StateDirectoryMode=0700`, so `/var/lib/bot-agent-runner` exists and is writable under `ProtectSystem=strict`. The helper creates `files/` under that directory. The other hardening stays: `ProtectSystem=strict`, `PrivateDevices=yes`, `RestrictAddressFamilies=AF_UNIX`. The socket is `AF_UNIX` and is not under `/dev`. `bot-agent.service` sets `InaccessiblePaths=-/run/docker.sock -/var/run/docker.sock -/var/lib/bot-agent-runner`. The leading `-` on the store path lets a host without that directory start. Joe reviews these unit lines before install.

Threat model, from spec §3: one root process opens the socket; nothing from a request reaches Docker as raw HTTP; projects and labels scope mutations; env values, registry tokens, and file contents are not returned; the policy ceiling is the image patterns, the project list, project volumes, managed files, the project bridge, and public ports only when `allow_public_ports` is set. The bind source of a managed file is built by the helper. A symlink or a failed ownership, mode, or link-count check is `bad_spec` and does not touch a container. Mounts are read-only and carry no `BindOptions`. The agent cannot open the store.

Managed files (v1.5) live at `/var/lib/bot-agent-runner/files/<project>-<entry>/<name>`, with `-prev` and `.new` slots beside the current one. The helper walks that directory from `/` with `openat` and `O_NOFOLLOW`, then creates slots and files only through `*at` calls. A service deploy writes `.new`, parks the current container and its slot as `-prev`, and renames `.new` into place before create. A job replaces its one slot. Rollback removes the current container and its slot, renames `-prev` and its slot back, and starts. If a container rename returns an error, the helper lists the entry again on a short context of its own, because the request context may already be cancelled, and moves the slot onto the name that container actually has. A container still named `-prev` gets that slot back. A rename that landed keeps the slot on the current name. The same list runs when parking the current container as `-prev` and when a failed start renames it back. If that list cannot show exactly one of the two names with this entry's labels, the slot stays put and the verb returns `docker_unavailable`. A start that fails after the container is back on `-prev` still moves the slot with it, so the names match. `container_remove` deletes the container and its slot. A missing `files/` directory, or a missing parent, on a verb with no files is "no store" and the container change still happens. A request with files creates `files/` when the parent exists. A missing parent on that request, and any other failure to open the store, changes nothing. When `files` is non-empty the container label `dev.deploybot.files_hash` is the hex SHA-256 of `<name>:<hex sha256 of content>\n` sorted by name. `container_status.files_hash` is that label, or `""` when there is none. The store path is not configurable from the request or from `runner.toml`.

`runner.toml` keys, all invalid when the value is the wrong shape: `images` (patterns), `projects` (slugs), `max_containers` (1..200, default 20), `allow_public_ports` (default false). `ImagesEnabled` is true only when the policy is valid and enabled, both lists are non-empty, and no listed project is another plus `-` plus more characters. When two projects overlap that way, the helper logs `bot-agent-runner: policy: overlapping projects <a> <b>` once on that connection. The example file leaves the four keys commented out and says that container access equals root.

Verbs: `image_pull`, `container_deploy`, `container_rollback`, `container_remove`, `container_start`, `container_stop`, `container_restart`, `container_status`, `container_logs`, `container_list`. Mutating entry verbs hold `flock` on `/run/bot-agent/image-<project>-<entry>.lock` for the whole verb. `container_status` and `container_logs` do not take that lock and do not create the file. At most 512 of those files are created. A further new name is `policy_denied` and does not dial. The file is not removed on unlock. `container_deploy` also holds `/run/bot-agent/image-count.lock` across the container count and the create, so the host cap covers every entry. Program verbs keep the helper-wide lock. Pull and list do not take the entry lock. Rollback reads the previous container's image from the helper's own list and refuses it unless that image is `repo@sha256:<64 hex>` and the repo is still in `images`.

Rollback for containers: `images = []`, or an empty `projects` list, makes the helper refuse image verbs. Containers already created keep running. Removing `/var/run/docker.sock` from `ReadWritePaths` is the other switch.

## Installer and `policy check`

`packaging/install.sh` is the host install path from v0.2.1. It ships in the release bundle and copies only files from that directory (no download). Subcommands are `check`, `install`, `enroll`, `upgrade`, `rollback`, and `remove`. State is `/var/lib/bot-agent-installer/` mode `0700` root: the installed version and the sha256 of every file the installer wrote, plus `prev/` for the last upgrade. Upgrade copies a replaced file to `<file>.prev` (one level). A failure after that backup is written restores it and exits 1. A successful upgrade keeps `.prev` until a later restore has been verified. When `/etc/bot-agent/env` exists, upgrade and rollback restart the agent whatever its previous state; `NRestarts` must be exactly 0 and `bot-agent version` must match, or the `.prev` set is restored. Without that file they do not restart and print `not enrolled: agent not restarted`. `--runner-config` is copied into the installer's private directory before `policy check`, and that copy is what gets installed. A symlink, a non-regular file, or a file writable by group or other is refused. From v0.2.7, `install --runner` and `check --runner` also take `--project SLUG` (once), `--image PATTERN` (1 to 20), and `--enable`, not with `--runner-config`. The shell checks each value against the slug and pattern grammar before any file is written (exit 2 otherwise), then writes `enabled`, `projects`, and `images` to a file in the private directory, which takes the `--runner-config` path (policy check, `root:root` `0644`, `policy-owned`, hash in the record). With `--enable` the check must print `images=true`. An existing `runner.toml` is kept only when it is byte-identical; a different one exits 1 and nothing changes. A bundle path with a character outside letters, digits, and `. _ / + -` is refused before anything changes. The staged re-exec passes these flags on, and the operator's bundle path in `BOT_AGENT_INSTALL_BUNDLE`; the staged run checks that path against the same allowlist and that its `install.sh` is byte-identical to the staged copy. A successful `install`, including one that finds the host already installed, prints `next: sudo <bundle>/install.sh enroll --server '<server URL>'` before the summary, with ` --runner` when `--runner` was passed or the installer record already has the helper. `remove` stops `bot-agent-runner@*.service` instances before deleting the template. A failed stop or disable of the agent, the socket, a running helper instance, or an owned unit is reported, the files are still deleted, and the summary is `remove incomplete` (exit 1). No matching helper instance is not a failure. A runner socket unit that is not installed is not a failure. Workload removal matches the label `dev.deploybot.owner=bot-agent`. `--remove-workloads` fails if docker cannot list containers, volumes, or networks. On an enrolled host (`/etc/bot-agent/env` exists), `upgrade --runner` runs `systemctl enable --now bot-agent-runner.socket` after `daemon-reload` and before the agent restart, because the agent probes the helper only at startup. That verification also requires `systemctl is-active bot-agent-runner.socket` to be `active`. Rollback on an enrolled host re-enables the socket when the restored set includes it, after `daemon-reload` and before the restart. When the rollback removes the socket, it runs `systemctl disable --now bot-agent-runner.socket` before deleting that unit file. A host without the env file enables nothing. When there is no installer record but `/usr/local/bin/bot-agent` exists, `check` and `upgrade` print `installed: <version> (not installed by the installer)` from `bot-agent version` only when that file is a regular non-symlink executable owned by root and not writable by group or other; otherwise they report `installed: none`. The upgrade summary is `upgraded <old> -> <new>`. A managed directory that is a symlink (`/usr/local/bin`, `/etc/systemd/system`, `/etc/bot-agent`, `/var/lib/bot-agent-installer`, `/usr/local/libexec`, `/etc/tmpfiles.d`, or the insecure-dev drop-in directory) is refused instead of followed. `enroll` passes the join token to `bot-agent init` on stdin. `--insecure-dev` writes the same drop-in as `install --insecure-dev` and passes `BOT_AGENT_INSECURE_DEV=1` to `init`. An existing `insecure-dev.conf` still counts when the flag is absent. `init` stores a server URL whose path is empty or `/` with `/agent/v1/ws` appended, and keeps any other path. When the agent unit is active, `enroll` restarts it; otherwise it runs `systemctl enable --now bot-agent.service`, then enables the runner socket when `--runner` is set or the helper is already installed. It waits up to 30 seconds for a non-empty `BOT_AGENT_HOST_ID` and `BOT_AGENT_CREDENTIAL_ID` and for `BOT_AGENT_JOIN_TOKEN` to be absent, using the same trim, `export`, and unquote rules as the agent, and checking key names only. After the keys appear it runs `systemctl reset-failed` on `bot-agent.service`, waits the same 15 second settle as upgrade, and then requires the agent active with `NRestarts` exactly 0. It does not delete the env file. If that check fails, recovery is `systemctl stop bot-agent`, move `/etc/bot-agent/env` aside, then enroll again. Missing keys exit 1 with `enroll failed: credential not persisted`. Success prints `summary: enrolled`. A real upgrade, rollback, or enroll prints each systemd step it takes, matching the dry-run line without the `dry-run:` prefix (`systemctl enable --now bot-agent-runner.socket`, `systemctl restart bot-agent.service`, and `systemctl disable --now bot-agent-runner.socket` when that step runs), then `verify: active, NRestarts 0, version <v>` and, when this command enabled the socket, `verify: runner socket active`.

`/etc/bot-agent` is `root:bot-agent` mode `1770` (sticky). The agent can create its temp file and rename it over `env`. The sticky bit stops it unlinking the root-owned `runner.toml`. Mode `0700` owned by `bot-agent` would let the agent unlink that file. `install`, `upgrade`, and `rollback` set and verify `1770`. The installer never overwrites an existing `runner.toml` or env file. It does not stop or delete legacy `bot_agent` units.

`bot-agent policy check FILE` calls `policy.Check`, which is `Load` with ownership and mode skipped. `run_as` is still resolved against passwd and group. The installer checks `runner.toml` itself for mode `0644` and, outside the test hook, owner root. Output is `valid` plus effective flags, or `invalid: <reason>`. Reasons are the policy package's tokens (`parse`, `unknown_key`, and the rest). File bytes are not printed. `programs` follows `Enabled` when the file is valid. `images` follows `ImagesEnabled` (valid, enabled, both lists non-empty, no overlapping project names). `image_patterns` is the pattern count even when images are not enabled, so a file can be valid and still leave images off.
