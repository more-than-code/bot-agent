# bot-agent

Host agent daemon and runner root helper for Deploybot: system metrics collection, process and network port tracking, service discovery, configurable TCP/HTTP health checks, and secure catalog workload execution (systemd programs and Docker container images) governed by local runner policy.

- Design: `docs/design.md`
- Contracts: `docs/contracts/agent-protocol-v1.md` and `docs/contracts/api-v1.md`

## Architecture & Security Model

`bot-agent` uses a two-tier privilege separation model designed for Linux hosts running systemd:

1. **Unprivileged Agent Daemon (`bot-agent`):** Runs as the dedicated unprivileged system user `bot-agent`. Sandboxed via systemd (`ProtectSystem=strict`, `ProtectHome=yes`, `NoNewPrivileges=yes`, empty capability sets, Docker and host socket paths inaccessible). Communicates outbound-only to `bot-api-server` over a WebSocket connection (`wss://<api-host>/agent/v1/ws`) with mutual token authentication. It opens no listening network ports on the host.
2. **Socket-Activated Root Helper (`bot-agent-runner`):** An optional root-privileged helper listening on a local UNIX domain socket (`/run/bot-agent-runner.sock`). The helper verifies caller credentials (`SO_PEERCRED`) to ensure only the local `bot-agent` UID can connect. Privileged operations (installing systemd units, interacting with Docker Engine API) are strictly governed by the root-owned policy file `/etc/bot-agent/runner.toml`.

A compromised API server or compromised agent daemon cannot execute commands outside what the host's root-owned `runner.toml` policy explicitly allows.

## bot-agent CLI

`bot-agent run` is the default and takes no arguments. `bot-agent version` prints the agent version. `init` reads the join token from stdin so it does not show up in process arguments:

```bash
printf '%s\n' '<token>' | bot-agent init --server '<wss-url>' --join-token-stdin
```

The token is one trimmed line, 16–128 characters of `[A-Za-z0-9_-]`. `--join-token <tok>` is rejected. Optional `--env-file` selects the env file (default `/etc/bot-agent/env`). Nothing from the env file is printed. A `--server` URL whose path is empty or `/` is stored with `/agent/v1/ws` appended. Any other path is kept as given. `BOT_AGENT_SERVER_URL` is that full URL.

`bot-agent policy check FILE` parses a `runner.toml` with the same rules as the agent. It prints `valid` and the effective flags (`enabled`, `programs`, `images`, `projects`, `max_containers`, `allow_public_ports`, `image_patterns`), or `invalid: <reason>` and exits 1. Ownership and mode are not checked. `run_as` is still resolved. The command does not print the file.

## Service Discovery & Health Checks

Discovered services are re-sent at least every 5 minutes while connected; see agent-protocol v1.2.

A services report is the host's full set, so it is sent only from a complete discovery. If the process scan fails, or the program policy is enabled and the owned-program lookup fails, or images are enabled and `container_list` fails, that cycle sends nothing and the previous report stays. `hello` carries `services_complete`. It is false, with `services` empty, when the first discovery did not finish, so the server does not treat that hello as the full set. See agent-protocol v1.3.2.

TCP and HTTP health checks configured in Deploybot run locally on the host against loopback (`127.0.0.1:<port>`). Results and latencies are streamed back to the server.

## Install and upgrade

A release bundle contains `install.sh`, `SHA256SUMS`, `bot-agent-vX-linux-{amd64,arm64}`, `bot-agent-runner-vX-linux-{amd64,arm64}`, and `units/`. The script installs only files from that directory. It does not download anything. Run it as root on a Debian-family host with systemd:

```bash
sudo ./install.sh check
sudo ./install.sh install --runner --runner-config /path/to/runner.toml
sudo ./install.sh enroll --server 'wss://<your-api-host>'
sudo ./install.sh upgrade
sudo ./install.sh rollback
sudo ./install.sh remove
```

The steps are in [docs/install.md](docs/install.md), and the bundles are on the [GitHub releases page](https://github.com/more-than-code/bot-agent/releases).

`check` confirms the architecture, systemd, and the bundle hashes, and reports what is already installed. With `--runner`, or when `runner.toml` is already there, it also runs `bot-agent policy check`. A non-empty `images` list makes it report whether `docker` is on `PATH`. `check` changes nothing. If `/usr/local/bin/bot-agent` is present and the installer has no record, `check` prints `installed: <version> (not installed by the installer)`, where `<version>` is the output of that binary's `version` command. It runs that binary only when it is a regular non-symlink file owned by root and not writable by group or other. Otherwise `check` reports `installed: none`.

`install` creates the system user and group `bot-agent` (no home, no login shell), installs the agent and `bot-agent.service`, and leaves the unit disabled until `enroll`. `--runner` also installs the helper, the socket, the template unit, the tmpfiles snippet, and `runner.toml`. The policy file is the `--runner-config` you pass, or a template with `enabled = false`. The installer copies `--runner-config` into a private directory before it checks the file, and installs that copy. It refuses a symlink, anything that is not a regular file, or a file writable by group or other. An existing `runner.toml` or `/etc/bot-agent/env` is kept. `--insecure-dev` writes a drop-in that sets `BOT_AGENT_INSECURE_DEV=1`. That flag is for a dev host.

`/etc/bot-agent` is `root:bot-agent` mode `1770` (sticky), so the agent can create its temp file and rename it over `env`, and cannot unlink the root-owned `runner.toml`. `install`, `upgrade`, and `rollback` set and verify that mode. `runner.toml` is `root:root` mode `0644`. The env file, once `enroll` writes it, is `bot-agent:bot-agent` mode `0600`. The binaries are `root:root` mode `0755`. Units and the tmpfiles snippet are `root:root` mode `0644`. If a directory the installer manages is already a symlink, the installer refuses it and does not follow the link. `/usr/local/bin` and `/etc/systemd/system` keep their existing mode when they are already directories.

`enroll` reads the join token from stdin and passes that stream to `bot-agent init --join-token-stdin`. On a terminal it prompts with echo off. The token is not an argument, an environment variable of the installer, or a temporary file, and the script does not print it. `--insecure-dev` writes the same drop-in as `install --insecure-dev` and passes `BOT_AGENT_INSECURE_DEV=1` to `init`. Without that flag, an existing `insecure-dev.conf` still counts. When `bot-agent.service` is already active, `enroll` restarts it. Otherwise it runs `systemctl enable --now bot-agent.service`. With `--runner`, or when the helper is already installed, it then enables `bot-agent-runner.socket`. It waits up to 30 seconds until the env file has a non-empty `BOT_AGENT_HOST_ID` and `BOT_AGENT_CREDENTIAL_ID` and no `BOT_AGENT_JOIN_TOKEN`. It reads the file the same way the agent does (trim, one leading `export `, unquote) and does not print the values. After those keys are present it runs `systemctl reset-failed` on `bot-agent.service`, waits the same settle interval as upgrade (15 seconds), and then requires the agent to be active with `NRestarts` exactly 0. It does not delete the env file. If that check fails, it exits 1. Recovery is one step: `systemctl stop bot-agent`, move `/etc/bot-agent/env` aside, then enroll again. If the keys do not appear, it exits 1 with `enroll failed: credential not persisted`. Success prints `summary: enrolled`.

`upgrade` refuses the same version unless `--force`. It copies each file it will replace to `<file>.prev` and records that set under `/var/lib/bot-agent-installer/prev/`. A unit whose hash does not match the installer's record is left alone unless `--force`. After the new files are in place it reloads systemd. When `/etc/bot-agent/env` exists, it restarts the agent whatever the unit's previous state, and requires `active`, `NRestarts` exactly 0, and `bot-agent version` equal to the bundle. With `--runner` on that enrolled host, it enables and starts `bot-agent-runner.socket` after the reload and before the restart, and verification also requires that socket to be `active`. Without the env file it does not enable the socket, does not restart, and prints `not enrolled: agent not restarted`. A failure after that backup is written, including a failed copy or a failed check, restores the `.prev` set and exits 1. A successful upgrade keeps `.prev` for a later `rollback`. `env`, an existing `runner.toml`, and drop-ins this installer did not write are not touched. A host with no installer record is reported as `installed: <version> (not installed by the installer)` from the existing binary when that binary passes the same root-owned, not group-or-other-writable check, and a successful upgrade summarizes `upgraded <old> -> <new>`. Adopting that host takes `--force`.

`rollback` restores that one previous set, then uses the same enrolled restart check as `upgrade`. When the restored set includes `bot-agent-runner.socket`, an enrolled host enables it again after the reload and before the restart. When the rollback removes that socket, it disables and stops it before deleting the unit file. A host without `/etc/bot-agent/env` does neither. A write that fails in the middle of that restore is tried again from `.prev` before the script exits 1. A second rollback does nothing.

`remove` stops running `bot-agent-runner@*.service` instances, then stops and deletes the agent and helper units, the tmpfiles snippet, and the binaries. It keeps `/etc/bot-agent` and `/var/lib/bot-agent-runner`. It lists `deploybot-*.service` units and containers labelled `dev.deploybot.owner=bot-agent`, and leaves them in place. `--remove-workloads` stops and deletes only units that carry both `X-Deploybot-Project=` and `X-Deploybot-Entry=`, removes those containers, and removes labelled networks. If docker cannot list containers, volumes, or networks, `--remove-workloads` fails after that units part and does not delete the agent files. If `systemctl disable --now` or `stop` fails for the agent, an installed helper socket, a running helper instance, or an owned unit, the script reports it, still deletes the files, and exits 1 with `summary: remove incomplete`. A helper stop that matches no instance is not a failure. A helper socket that was never installed is not a failure. Volumes stay unless `--purge` is set as well. `--purge` also deletes `/etc/bot-agent`, `/var/lib/bot-agent`, `/var/lib/bot-agent-runner`, and the `bot-agent` user. The group is left in place. Every remove tells you to revoke the host in the console.

`--dry-run` prints the writes and deletes and changes nothing. On an enrolled host it also prints the runner-socket enable or disable that `upgrade --runner` or `rollback` would run, and it does not call `systemctl` for that step. A real `upgrade`, `rollback`, or `enroll` prints each systemd step it takes, in the same words without the `dry-run:` prefix: `systemctl enable --now bot-agent-runner.socket`, `systemctl restart bot-agent.service`, and `systemctl disable --now bot-agent-runner.socket` when that step runs. After the check passes it prints `verify: active, NRestarts 0, version <v>`, and `verify: runner socket active` when this command enabled the socket. Exit 0 means the command finished, including "nothing to do". Exit 1 is a failure; a failed precheck also prints `nothing changed`. Exit 2 is usage. `--root` is test-only and is refused unless `BOT_AGENT_INSTALLER_TEST=1`.

## Programs (agent-protocol v1.3.1)

`bot-agent` stays an unprivileged user. `packaging/bot-agent.service` keeps `NoNewPrivileges=yes`, an empty `CapabilityBoundingSet=` and `AmbientCapabilities=`, `ProtectSystem=strict`, and `ProtectHome=yes`. It hides the Docker sockets and the managed-file store with `InaccessiblePaths=-/run/docker.sock -/var/run/docker.sock -/var/lib/bot-agent-runner`. The leading `-` lets a host that has no such path start. That sandbox cannot see `/home` and cannot run a useful `sudo`. The agent therefore does no filesystem checks on a program directory. It dials `/run/bot-agent-runner.sock`. The root helper re-reads `/etc/bot-agent/runner.toml`, resolves the directory and the executable, and writes an installed system unit under `/etc/systemd/system`.

The helper is socket-activated. There is no sudoers line.

- `bot-agent-runner.socket` listens on `/run/bot-agent-runner.sock` with `SocketUser=root`, `SocketGroup=bot-agent`, `SocketMode=0660`, and `Accept=yes`.
- Each connection starts `bot-agent-runner@.service` as root. `ExecStart` is `/usr/local/libexec/bot-agent-runner serve-conn`. The process reads one newline-terminated request from the socket and writes one JSON response.
- `serve-conn` checks `SO_PEERCRED` on that socket. The peer uid must be the `bot-agent` account. Anyone else is refused.

A compromised API cannot widen what this host will run: the policy file is root-owned and is not writable by `bot-agent`. A compromised agent can ask only for what that policy already allows, and only by connecting to that socket. Polkit is not a substitute. It can limit unit names, not the command a unit runs. Shell mode (`/bin/sh -c`) is off unless `allow_shell` is true. Request env values are written to the root-only env file and are not logged. Keys that change which code runs (`LD_*`, `DYLD_*`, `NODE_OPTIONS`, and the rest of the v1.6.1 list) are refused, including a hoisted `KEY=value` argument.

`ProtectHome=read-only` on a program unit leaves other home directories readable. That follows from the policy model: the host owner chooses `run_as`, and that account can read whatever its own permissions already allow. An allowlisted interpreter such as `/usr/bin/node` runs the caller's arguments as `run_as`. The host owner chooses `exec_allow`. The helper does not try to decide which of those arguments are safe.

The helper unit is hardened only as far as its job allows. It must write `/etc/systemd/system` and `/var/lib/bot-agent-runner/programs`, keep `/run/systemd/system` writable while a wave-1 unit is still there, create `/run/bot-agent` (the helper lock, the image locks, and the old env directory), run `systemctl` and `journalctl`, read `/home` and `/proc`, and, when image containers are enabled, open `/var/run/docker.sock`. `packaging/bot-agent-runner@.service` sets `ProtectHome=read-only`, `PrivateTmp=yes`, `ProtectKernelModules=yes`, `RestrictAddressFamilies=AF_UNIX`, `NoNewPrivileges=yes`, `RuntimeMaxSec=900`, and `ReadWritePaths` including `/etc/systemd/system` and `/var/run/docker.sock`. It also sets `StateDirectory=bot-agent-runner` and `StateDirectoryMode=0700`, which creates `/var/lib/bot-agent-runner` where `ProtectSystem=strict` would otherwise hide it. The helper creates `programs/` under that directory. The comments in that file say why a stricter sandbox is omitted. Opening that socket is root-equivalent.

Install, as root:

| Path | Owner | Mode |
|---|---|---|
| `/usr/local/libexec/bot-agent-runner` | `root:root` | `0755` |
| `/etc/systemd/system/bot-agent-runner.socket` | `root:root` | `0644` |
| `/etc/systemd/system/bot-agent-runner@.service` | `root:root` | `0644` |
| `/etc/tmpfiles.d/bot-agent-runner.conf` | `root:root` | `0644` |
| `/etc/bot-agent` | `root:bot-agent` | `1770` |
| `/etc/bot-agent/env` | `bot-agent:bot-agent` | `0600` |
| `/etc/bot-agent/runner.toml` | `root:root` | `0644` |

`/etc/bot-agent` stays `1770` (sticky) and group `bot-agent` so the agent can read the policy, write its own env file, and cannot replace `runner.toml`. Copy `packaging/runner.toml.example` (it ships with `enabled = false`) and `packaging/tmpfiles.d/bot-agent-runner.conf`, install the two units, then:

```bash
systemd-tmpfiles --create /etc/tmpfiles.d/bot-agent-runner.conf
systemctl daemon-reload
systemctl enable --now bot-agent-runner.socket
```

`/run` is empty at boot. The tmpfiles snippet creates `/run/bot-agent` and `/run/bot-agent/env` as `0700` `root:root`. The helper unit lists `-/run/bot-agent` so a missing directory does not fail namespace setup, and the helper creates those directories itself when it can. Program units are installed, not transient. The helper writes `/etc/systemd/system/deploybot-<project>-<entry>.service` as root `0644`, ending with `[Install]` and `WantedBy=multi-user.target`, and writes the env file and the validated start request as root `0600` under `/var/lib/bot-agent-runner/programs/` (the directory is `0700`). The unit's `EnvironmentFile=` is that programs path. `start` writes the env file, then the spec, then the unit, then runs `daemon-reload`, `enable`, and `restart`. A `\` in the directory, the executable, or the `run_as` home is `policy_denied` before any write. A drop-in at `/etc/systemd/system/<unit>.d` or `/run/systemd/system/<unit>.d` (any type) is `io_error` before `enable` on `start` and `restart`. The helper never creates or removes a drop-in. A `restart` of a unit already in `/etc` does not rewrite it, and still runs `daemon-reload`, `enable`, and `restart`. systemd starts an enabled unit at boot, so a program that was running comes back after a reboot with no agent involved. `stop` runs `disable`, then `stop`, then removes every regular file among the `/etc` unit, env, and spec and an owned `/run` copy. It keeps going when one of those cannot be removed, never unlinks a symlink or other non-regular file, then runs `daemon-reload`. If a file it tried to remove is still there, the reply is `io_error`. A later stop with no unit file removes a leftover spec whose stored project and entry match, and the regular env beside it, and does not report success while that spec remains. Otherwise a stopped program leaves no file in those directories and does not come back at boot. A start whose `daemon-reload` or `enable` fails, or whose unit does not become freshly active, disables and stops that unit, removes the `/etc` unit, env, and spec and an owned `/run` copy, then runs `daemon-reload`. A failed start leaves no file when that cleanup finishes. If a file cannot be removed, or `disable` fails, the reply is `io_error`. If `daemon-reload` fails while `restart` is moving a unit off `/run`, the helper removes the `/etc` files it just wrote and leaves the `/run` files, with no `disable`, `stop`, or second reload. If `enable` fails after that reload, the helper removes those `/etc` files and runs `daemon-reload` again so the `/run` unit is what systemd has loaded. Both replies are `start_failed` with `fresh` false. `max_programs` counts every unit file still on disk, including inactive ones. A name present under both `/etc` and `/run` counts once. Restart reads the stored request and refuses it, stopping the unit and removing its files, when the current policy would no longer allow that command. The next `start` of a unit this helper still owns in `/run/systemd/system` writes the `/etc` copy and then removes the `/run` unit and `/run/bot-agent/env/<unit>.{env,json}`. `restart` writes that `/etc` copy only when it is missing, and removes the `/run` files only after `enable` succeeds. `stop` removes that `/run` copy together with any `/etc` copy. `status`, `logs`, `sockets`, and `list` look in `/etc/systemd/system` first, then `/run/systemd/system`. A unit file with our name but without our markers is not written, enabled, disabled, or removed. With our unit in `/etc`, a foreign same-name file in `/run` is left untouched and does not block the verb; a foreign file in `/etc` always refuses with `not_created`, and an owned `/run` unit behind it still counts for `max_programs` but `list` does not return it. Program units also set `PrivateDevices=yes`, `ProtectKernelTunables=yes`, `ProtectKernelModules=yes`, and `ProtectControlGroups=yes`, and they hide the docker, containerd, and podman sockets.

Rollback for programs: `systemctl disable --now bot-agent-runner.socket`, or set `enabled = false` and restart `bot-agent` (the agent reads the policy only at startup). Either one stops new program tasks. Units that are already enabled keep running, and they come back at the next boot, until an administrator runs `systemctl disable --now 'deploybot-*'` and removes the unit, env, and spec files. After `enabled = false` the agent stops reporting those units as owned services.

## Images (agent-protocol v1.4)

The same helper speaks the image verbs. The agent stays unprivileged and still dials `/run/bot-agent-runner.sock`. One root process, `bot-agent-runner`, opens `/var/run/docker.sock` (Engine API `/v1.47`). The helper builds every Engine request from typed fields. A request never arrives at Docker as a path, query, header, or body.

Threat model, from spec §3:

- One root process opens the socket. The agent unit keeps the Docker sockets inaccessible.
- No pass-through. Verbs are typed JSON, one object per connection. `exec`, `attach`, and archive are not reachable.
- `runner.toml` lists the project slugs this host may run. The helper writes `dev.deploybot.owner`, `host`, `project`, and `entry` itself. A container under `<project>-<entry>` or `<project>-<entry>-prev` with different labels is `conflict`, and nothing is changed.
- Env values, registry tokens, and secret file contents reach the agent in the task frame and are passed to the helper for that task. A compromised agent can read the secrets of the tasks it receives. That is the same trust the agent already has for its host (spec §3.4). The helper does not return them. List and status are projections. Results and log lines are redacted for the registry token and the secret-file values described under managed files, and for env values: every env value when `secret_keys` is absent, or only the listed keys when `secret_keys` is present. A listed key that is not in `env` is `bad_spec`. Values of at least 6 bytes are matched as the raw bytes, standard and URL base64 (padded and raw), and both JSON-escaped forms, and then with the v1.0.1 regex. Deploybot replaces an env secret with its preview: the first four runes and `…` when the value has at least 16 runes, otherwise `••••`. The registry token and secret-file pieces stay `[REDACTED]`. `outcome`, `digest`, `exit_code`, and status fields are passed through as the helper returned them. Lines are cut to 2048 characters and 64 KiB after that. A deploy or rollback tail sends the token and file pieces as `container_logs` `redact` and the env values as `redact_env`. Each list is at most 2048 values, each 6–4096 bytes, at most 512 KiB, and has no NUL. The helper applies those forms to each raw line before the regex and the cut, and it does not log or return either list. `image_logs` sends neither list. That filter is best-effort, not a boundary: a command can print a value in another encoding or send it off the host (spec §12.9).
- A caller can ask only for the image patterns, the listed projects, project volumes, the project bridge network, and managed files. The only host bind mounts are the read-only file mounts the helper builds itself. There are no extra capabilities, devices, or host namespaces. A public port needs `allow_public_ports`.

Verbs: `image_pull`, `container_deploy`, `container_rollback`, `container_remove`, `container_start`, `container_stop`, `container_restart`, `container_status`, `container_logs`, `container_list`. Program verbs keep `{"ok":false,"reason":"..."}`. Image verbs return `{"error":"policy_denied"|"bad_spec"|"conflict"|"docker_unavailable"|"image_unavailable"}` or the success object in the v1.4 table. The agent accepts either refusal shape.

The agent does not import the helper. Task kinds are `image_deploy`, `image_rollback`, `image_remove`, `image_start`, `image_stop`, `image_restart`, `image_status`, and `image_logs`. `service` is null. An unknown spec key, a missing required key, or a non-null `service` is `bad_spec` before the policy is consulted. After the v1.0 host, expiry, and kind checks, an image task is refused in this order: images are not enabled (`policy_denied`); `project` is not in `projects` (`policy_denied`); the ImageSpec or the entry fields fail (`bad_spec`); the image does not match a pattern (`policy_denied`). Start, stop, restart, status, remove, and logs have no ImageSpec and no pattern check. `image_logs` checks `lines` (1..2000) after the policy and the project. An image task spec may be as large as the agent frame (1 MiB). Image verbs on the helper accept up to 2 MiB. Program verbs stay at 64 KiB. A helper body over its verb's limit finishes as outcome `failed`.

`hello.programs.images` is true when the policy is valid and enabled, both lists are non-empty, and no listed project is another plus `-` plus more characters. `hello.programs.docker` is true when `container_list` succeeded on the first discovery of this process. The first answer latches the flag. `hello.programs.files` is true whenever that object is sent: this agent and its helper implement managed files. It does not depend on the policy. `hello.programs.docker_health` and `hello.programs.healthcheck` are true the same way: this agent implements Docker health samples and ImageSpec `healthcheck`. `hello.programs.logging` is true the same way: Deploybot caps every container it creates with the json-file driver at `max-size` 10m and `max-file` 3 unless the ImageSpec sets `logging`. Patterns and project lists are not sent. The flags are present whenever the policy file exists, including when `images` or `docker` is false. There is no images capability.

An image task honours the frame's `timeout_sec` for the whole sequence, clamped to at most 4020 seconds. Zero or negative uses 15 seconds. Service deploy pulls, then reads `container_status`. A running container with this digest, this `spec_hash`, and this `files_hash`, and `force` false, is `unchanged`. When the spec has a `healthcheck`, `unchanged` also requires that container's `container_list` health to be `healthy`. The agent computes the expected `files_hash` from the task. With no files that value is empty. Otherwise the agent deploys and waits. A configured health check whose service is the entry, whose protocol is `http` or `tcp`, and whose port is one of the spec's host ports is probed on `127.0.0.1`. One passing round while the container is `running` is success. With no such check, the container must stay `running` with `restart_count` 0 for `healthy_after_sec`, polled every 2 seconds. A service whose spec has `healthcheck` waits on `container_list` instead: every 2 seconds until `health` is `healthy` and any configured checks pass. `starting` keeps waiting. `unhealthy`, or the wait limit `max(timeout_sec, start_period_sec + interval_sec × (retries + 1))`, calls `container_rollback` only when the container before this deploy was `running`, and otherwise stops the new container and reports `failed`. `image_rollback` waits the same way. Without `healthcheck` the wait is unchanged. `timeout_sec` in that limit is the task frame timeout (a service spec's `timeout_sec` is 0). A failed wait calls `container_rollback` only when the container before this deploy was `running`: `rolled_back`, or `rollback_failed` when that call fails. Any other state stops the new container and reports `failed`, and a parked container stays on `-prev`. A `container_status` error during that wait, including `docker_unavailable`, is outcome `failed` and does not roll back. A job pulls, removes the container when one is present, deploys, and polls every 2 seconds until `exited` or the spec's `timeout_sec`. Exit 0 is `succeeded`. Any other exit is `failed` with `exit_code`. A timeout stops the container and the outcome is `timeout`. Cancelling the task context is `failed` and does not stop the container. A service `image_rollback` whose digest equals `container_status` `prev.digest` does not pull or deploy: it calls `container_rollback` (the kept `-prev` container and its slot come back), waits healthy as a rollback deploy does (`healthy_after_sec`, at least 30 seconds, or the `healthcheck` wait when the spec has one), and reports `succeeded` with that digest, or `failed` when the swapped container is not healthy. Any other digest, and a job rollback, is still that service sequence, pulling `<name>@<digest>`. Start, stop, restart, status, remove, and logs are one verb each.

`task_result.status` is `succeeded` for outcomes `succeeded` and `unchanged`. Every other outcome is `failed` with `error_code` set to the outcome. `image_unavailable` and `conflict` stay those outcomes. `policy_denied` and `bad_spec` from the helper become `forbidden_spec`. `docker_unavailable` and a transport failure become `failed`.

When images are on, every discovery cycle calls `container_list`. A container with all four `dev.deploybot.*` labels, this host's label, and a project in `projects` is an owned service whose name is exactly its entry, with `owner.kind` `image` and `image_digest` set when the digest is `sha256:` plus 64 hex. A non-owned row that already uses that name is renamed. An owned row that already uses it, including an owned program, keeps the name, and the extra container is not given a suffixed name. The host label is the first 16 hex characters of SHA-256 of `/etc/machine-id` when the agent can read that file. If it cannot, any non-empty host label is accepted, and the agent logs that once without the path. A `<project>-<entry>-prev` container with the same four labels is not a second service; its published ports are still kept off the unmapped list. If only the `-prev` container exists, it is the owned service and `container_name` keeps that name. Every other container is `kind` `container`, named by its container name without one leading `/`, with `image_digest` null and `"owner":null`. A name outside the service name pattern is sanitized; `container_name` keeps the trimmed Docker name. Published host ports are not also reported as unmapped listeners. The helper returns at most 200 containers, Deploybot-labelled rows first, and sets `truncated` when it cut. A truncated list is still complete, and the agent logs that once. Each item includes `health`: `healthy`, `unhealthy`, `starting`, or null. The helper reads the Engine's structured `Health.Status` when that object is present (the API v1.52 list field), and otherwise the `Status` suffix `(healthy)`, `(unhealthy)`, or `(health: starting)`. While `config.docker_health` is true, each complete discovery pass emits one `health` sample per container service whose health is `healthy` or `unhealthy` (`protocol` `docker`, `result` `success` or `unhealthy`, `http_status` and `latency_ms` null). `starting` and null emit nothing. The pass before `hello_ok` has not seen the flag, so it emits none. A failed `container_list` makes that cycle incomplete.

Env values, `registry_auth.token`, and file contents are wiped from the task spec when the task ends. The pending result does not carry them. The merged env and the file contents sent to `container_deploy` hold the real values, and the token is sent on `image_pull`. `spec.secret_env` stays the `<set>.<KEY>` reference. `spec.files` stays names and targets.

`packaging/runner.toml.example` leaves these four keys commented out. Uncommenting them gives the helper root-equivalent container access.

| Key | Meaning |
|---|---|
| `images` | Anchored reference patterns. `*` is one path component. The host is literal. |
| `projects` | Project slugs this host may run. |
| `max_containers` | 1..200 Deploybot-labelled containers, default 20. |
| `allow_public_ports` | When false, a `public` port is `policy_denied`. |

An invalid key or value makes the whole policy invalid. An empty `images` or `projects` list is valid and leaves image verbs off. When one listed project is another plus `-` plus more characters, as with `acme` and `acme-web`, the policy stays valid for programs and image verbs are refused.

Rollback for containers: set `images = []` (or remove `projects`) in `runner.toml`. The helper then refuses image verbs. Containers it already created keep running under their restart policy. Remove them by hand if they should stop. Taking `/var/run/docker.sock` out of `ReadWritePaths` is the other switch.

## Managed files (agent-protocol v1.5)

`image_deploy` and `image_rollback` carry a top-level `files` list, in the same order as `spec.files`. Each item is `name`, `target`, `content`, and `secret`. Content is not stored in `spec.files`. The agent checks the two lists one for one, and it checks the name, content, and target rules (api-v1 v1.9 rules 1–2 and 13, including a file target under a volume target and the reverse). That failure is `bad_spec`, the same task reject as any other bad image spec. The helper checks the same rules again on `container_deploy` and returns `bad_spec`.

The helper keeps the bytes at `/var/lib/bot-agent-runner/files/`. One slot directory per container: `<project>-<entry>`, `<project>-<entry>-prev`, and the transient `<project>-<entry>.new`. A file is `<slot>/<name>`. Slots are mode 0700 and files are mode 0444, both root-owned. The helper opens the store with `O_DIRECTORY|O_NOFOLLOW` and then only uses `openat`, `mkdirat`, `renameat`, and `unlinkat` on directory handles. It does not follow a symlink. Before every use it checks that the store and the slot are directories owned by root with mode 0700, and that each file is a regular file owned by root, mode 0444, link count 1. Anything else is `bad_spec`, and that verb does not change a container or delete the bad entry. A verb with no files treats a missing `files/` directory, or a missing parent of it, as "no store" and continues without creating either. A request that carries files creates `files/` when the parent already exists. A missing parent on that request is `docker_unavailable` and changes nothing; the helper does not create the parent. Any other I/O error opening the store is `docker_unavailable` and changes nothing.

Each file is one bind mount, `ReadOnly: true`, with no `BindOptions`. `Source` is always `/var/lib/bot-agent-runner/files/<slot>/<name>`. The helper builds that string. It is not taken from the request. When `files` is non-empty the container gets the label `dev.deploybot.files_hash`, the hex SHA-256 of the lines `<name>:<hex sha256 of content>`, sorted by name, each line ending in a newline. With no files the label is absent. `container_status` returns it as `files_hash`, or `""` when the container has none. Projections do not include content, slot paths, or mounts.

Trust boundary, from the catalog spec §3:

- The bind source is never a path from the request.
- A symlink, a wrong mode, a wrong owner, or a link count other than 1 refuses deploy, rollback, and remove before any container is touched.
- Mounts are read-only. There is no `BindOptions`, so propagation stays Docker's default.
- The agent unit cannot open the store (`InaccessiblePaths=-/var/lib/bot-agent-runner`). The agent sees secret contents only inside the task frame.
- Secret file contents are redacted by exact value. The whole content is included when it is 6–4096 bytes. Every trimmed line of 16–4096 bytes is included. When the content parses as JSON, every string value of 16–4096 bytes is included, and so is every trimmed line of that size inside a string value, which covers a PEM line printed on its own. A plain file adds nothing.

`container_logs` `redact` holds at most 2048 of those values, each 6–4096 bytes, at most 512 KiB altogether, and no NUL. A deploy tail clips the list to that cap. The exact set kept in the agent process still covers a value the list had to drop. Results and the agent's own logs do not contain file content.

`StateDirectory=bot-agent-runner` is what makes `/var/lib/bot-agent-runner` writable for the root helper. The helper creates `files/` only for a request that carries files, and only when that parent already exists. A missing parent on a request with files is `docker_unavailable` and does not change a container. A verb with no files still deploys, rolls back, or removes the container when `files/` or its parent is missing, and it does not create either directory. These two unit lines, and the agent's `InaccessiblePaths` entry, are host security settings. Review them before install. Install the helper unit, so the state directory exists, before deploying an entry that has files.
